Patrones y herramientas con los que la comunidad hace que un modelo fuerte dirija y otro barato programe, con métricas de repos e integración con git.

Informe de un frente de la investigación. Síntesis y decisiones en [[orquestacion-opus-deepseek-informe]].

Diseño objetivo: Claude Opus (Claude Code, plan Pro, rate-limited, NO API) como orquestador/planificador/revisor; DeepSeek (API oficial, pago por token) como escritor de código masivo. Todo cambio con tests. Git con `main` protegida, ramas cortas, PRs, CI. Usuario: ingeniero DevSecOps senior. Criterio: lo contrastado por la comunidad gana a lo nuevo/hype. Lo sin evidencia de uso real se marca «prometedor sin contrastar».

## 1. Patrones identificados

### 1.1 Architect / Editor (Aider)
Un modelo "arquitecto" (razonamiento fuerte) propone el plan en lenguaje natural; una segunda llamada a un modelo "editor" (rápido/barato) traduce esa propuesta a ediciones de fichero en el formato de diff de Aider. Existe porque los modelos frontera razonan bien pero a veces generan diffs mal formados, mientras que modelos baratos son precisos en el formato pero peores razonando.
- Handoff: dos llamadas encadenadas dentro del mismo proceso Aider; el "contrato" es el texto de la propuesta del arquitecto, no un fichero de spec externo.
- Verificación: no hay revisor automático nativo — el propio flujo produce el diff y lo aplica; la verificación queda en manos del usuario o de hooks de lint/test que Aider puede ejecutar tras aplicar (`--auto-test`).
- Fuentes: [Separating code reasoning and editing | aider](https://aider.chat/2024/09/26/architect.html), [Chat modes | aider](https://aider.chat/docs/usage/modes.html), [Architect Mode | DeepWiki](https://deepwiki.com/Aider-AI/aider/5.5-architect-mode).
- Evidencia de uso real: issue de usuario usando exactamente el patrón propuesto (OpenRouter R1 como arquitecto, Sonnet como editor, `deepseek-chat` como "weak-model") — [Aider-AI/aider#3095](https://github.com/Aider-AI/aider/issues/3095).

### 1.2 Modelo distinto por modo (Roo Code / Kilo Code / Cline)
Estas extensiones VS Code tienen "modos" (Architect/Plan, Code/Act, Orchestrator, Debug, Ask) y permiten asignar un proveedor/modelo distinto a cada modo; el modo Orchestrator descompone la tarea y delega subtareas a otros modos ("Boomerang Tasks" en Roo/Kilo: la subtarea "vuelve" al orquestador con el resultado).
- Handoff: dentro de la misma sesión de la extensión, mediante subtareas con su propio contexto y system prompt por modo; no hay fichero de spec intermedio — el propio orquestador construye el prompt de la subtarea.
- Verificación: el modo Orchestrator puede revisar el resultado antes de marcar la subtarea como completa, pero es prompt-driven, no un gate automático con tests obligatorios.
- Fuentes: [Using Modes | Roo Code Docs](https://docs.roocode.com/basic-usage/using-modes), [Boomerang Tasks | Roo Code Docs](https://docs.roocode.com/features/boomerang-tasks), [Multi-Agent Workflows With Roo Code | Xebia](https://xebia.com/blog/multi-agent-workflow-with-roo-code-2/), [Plan & Act Mode | Cline Docs](https://docs.cline.bot/core-workflows/plan-and-act), [Integrate with Kilo Code | DeepSeek API Docs](https://api-docs.deepseek.com/quick_start/agent_integrations/kilo_code/).
- Problema real y documentado: en Kilo Code, con DeepSeek V3.1 el Orchestrator "salta" el modo Architect y va directo a Code, generando tareas demasiado grandes que exceden el contexto — [Kilo-Org/kilocode discussion #2580](https://github.com/Kilo-Org/kilocode/discussions/2580).

### 1.3 Spec / acceptance-criteria como contrato (spec-driven development)
Patrón identificado en la literatura 2026: en vez de una instrucción conversacional, el modelo fuerte redacta una spec con objetivo, restricciones, ficheros/áreas en scope y criterios de aceptación verificables (pass/fail), y esa spec es el contrato que recibe el ejecutor. En sistemas multi-agente se recomienda una interfaz tipada entre agentes en vez de un hand-off conversacional suelto.
- Dato relevante para el caso Opus→DeepSeek: en modelos frontera el formato de la spec apenas importa, pero en modelos no-frontera el formato produce diferencias de calidad de 0.83–2.42 puntos, y las specs "code-proximate" (contratos OpenAPI/TypeScript) triplican la cobertura de rutas API en el modelo más débil frente a specs en prosa. Esto es evidencia directa a favor de que, si DeepSeek hace el código, el hand-off debe ser spec formal/tipada, no prosa.
- Fuentes: [Acceptance Criteria Agents Can Actually Execute | Tekk.coach](https://tekk.coach/spec-driven-development/acceptance-criteria-agents-can-actually-execute/), [How to write a good spec for AI agents | AddyOsmani](https://addyosmani.com/blog/good-spec/), [Architecture as Capability Equalizer for Coding Agents (arXiv 2608.21747)](https://arxiv.org/pdf/2608.21747), [SDAD: Spec-Driven Agentic Development (arXiv 2608.20341)](https://arxiv.org/pdf/2608.20341).
- Nivel de evidencia: los papers arXiv son investigación reciente (agosto 2026), no herramienta con adopción medible — marcar **prometedor sin contrastar** en cuanto a "producto"; el patrón en sí (spec con acceptance criteria en el issue/PR description) sí está contrastado como práctica de ingeniería (Tekk.coach, AddyOsmani son guías de práctica, no papers).

### 1.4 Revisor separado sobre el PR (review loop)
El patrón más contrastado en producción real: el modelo barato escribe, y una segunda pasada (modelo fuerte o el mismo modelo barato en otra llamada) revisa el diff del PR contra la descripción/spec, comenta inline, y opcionalmente bloquea el merge. Existe tooling ya empaquetado para esto sobre DeepSeek concretamente.
- `hustcer/deepseek-review`: Action de GitHub que llama a DeepSeek para revisar cada PR y postea un comentario "sticky" (se actualiza, no se duplica); gatea forks/drafts/bots para no quemar presupuesto de API. Fuente: [hustcer/deepseek-review](https://github.com/hustcer/deepseek-review), [DeepSeek CR · GitHub Marketplace](https://github.com/marketplace/actions/deepseek-cr).
- `nexpeakcore/deepseek-harness-pr-review`: revisión "claim-by-claim" — verifica lo que dice la descripción del PR contra el código real, con humano-en-el-loop. Fuente: [nexpeakcore/deepseek-harness-pr-review](https://github.com/nexpeakcore/deepseek-harness-pr-review).
- Patrón explícito "barato extrae, caro revisa casos límite": DeepSeek para pasos sensibles a coste, Opus para pasos que requieren razonamiento fino — descrito en guías de práctica, no medido cuantitativamente. **Prometedor / práctica emergente, sin contraste cuantitativo fuerte.**
- El propio Claude Code ya trae este patrón nativo vía skill `/code-review` (revisor separado sobre el diff, con niveles de esfuerzo y modo `--comment` para postear inline) — es la pieza que ya tienes disponible en este entorno para el rol de "Opus revisor".
- Fuente adicional: `anthropics/claude-code-action` corre el runtime completo de Claude Code dentro de un runner de GitHub Actions y puede responder a menciones `@claude`, revisar PRs abiertos empujando directamente a la rama, y ejecutar automatizaciones programadas — [claude-code-action usage.md](https://github.com/anthropics/claude-code-action/blob/main/docs/usage.md), [Claude Code GitHub Actions Docs](https://code.claude.com/docs/en/github-actions).

## 3. Integración con git

- **Worktrees por tarea**: patrón ya estándar en 2026 para correr agentes en paralelo — cada agente obtiene su propio directorio de trabajo y rama, compartiendo el almacén de objetos `.git`. Descrito como "línea base por defecto" (no técnica avanzada) en múltiples guías 2026. Fuentes: [Git Worktrees for AI Coding | MindStudio](https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents), [Git Worktrees + Claude Code: 2026 Playbook | Developers Digest](https://www.developersdigest.tech/blog/git-worktrees-claude-code-parallel-agents-guide), [Git Worktree Isolation Patterns | Zylos Research](https://zylos.ai/research/2026-02-22-git-worktree-parallel-ai-development/).
- **Límite reconocido por el propio ecosistema**: worktrees aíslan el checkout, no el significado — "puedes crear conflictos de merge entre worktrees sin saberlo" (cita del equipo GitButler); los conflictos "semánticos" (código que compila pero rompe un contrato entre módulos) sobreviven a un setup de worktree correcto. Fuente: citada dentro de [MindStudio, Running Coding Agents in Parallel](https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents).
- Claude Code tiene soporte nativo de worktree vía el harness (tool `EnterWorktree`/`ExitWorktree` visto en este mismo entorno), consistente con el patrón de la comunidad.
- **Merge queue como cuello de botella nuevo**: con agentes generando más PRs que humanos escribiendo, la cola de merge (Graphite, Mergify) pasa a ser el cuello de botella — "el volumen de PR se duplicó, los merges siguen arrastrándose por una cola dimensionada para velocidad de tecleo humana". Dato citado (sin verificación metodológica propia, cifra de terceros): PRs con asistencia de IA rompieron `main` el 1.9% de las veces frente a 4.4% en PRs sin asistencia de IA detectable. Fuente: [Merge Queues Were Built for Humans. AI Agents Need More. | Mergify](https://mergify.com/blog/merge-queues-and-ai-coding-agents), [The Merge Queue Is the New Bottleneck](https://tianpan.co/blog/2026-07-02-the-merge-queue-is-the-new-bottleneck), [State of Merge Queues 2026 | Mergify](https://mergify.com/reports/state-of-merge-queues-2026).
- Dato relevante y no anticipado: Cursor (Anysphere) adquirió Graphite en diciembre 2025 — señal de que el mercado ve la cola de merge como pieza crítica de la cadena agente→PR. Fuente: mencionado en [Graphite merge queue guide](https://graphite.com/guides/merge-queue-tools-options) (verificar fecha exacta de la adquisición si se cita formalmente, aquí reportado como lo dio la búsqueda — **revisar antes de citar en otro documento**).
- Recomendación práctica implícita en las fuentes para el diseño Opus/DeepSeek: rama corta por tarea (o worktree), CI obligatorio con tests (ya es requisito del diseño), gate de review (humano u Opus) antes de la cola de merge, y cola de merge real (no solo "squash and merge" manual) si el volumen de PRs generados por DeepSeek crece.

| **OpenHands como orquestador principal** | Es un agente/orquestador completo alternativo a Claude Code, no una pieza que se inserte en un diseño donde Opus-vía-Claude-Code-Pro es fijo como orquestador. Útil solo como referencia arquitectónica (microagents/Skills por repo, resolver de issues→PR). |
| **Roo/Kilo Orchestrator mode con DeepSeek como planificador de subtareas** | Problema documentado de que el Orchestrator salta el modo Architect con DeepSeek 3.1 y genera subtareas sobredimensionadas — indica que DeepSeek no es fiable en el rol de planificador/orquestador, coherente con el diseño original de que ese rol lo haga Opus. |
