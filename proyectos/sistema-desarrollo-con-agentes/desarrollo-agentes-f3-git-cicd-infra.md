Branching, protección de ramas, merge queues, forja, CI/CD y despliegue a pequeña escala, y efecto de la IA en las métricas DORA.

Informe de un frente. La síntesis, con las decisiones pendientes, está en [[desarrollo-agentes-investigacion]].

## 1. Pregunta

Sistema de desarrollo genérico donde Claude planifica (casos de uso → issues) y agentes IA (DeepSeek) implementan issues como PRs con tests, potencialmente muchos PRs en paralelo. Apps variadas (Python, Node.js), despliegue mayoritariamente self-hosted en servidor doméstico, pero el sistema debe ser genérico. Se pregunta, con evidencia rigurosa:

1. Estrategia de branching (GitFlow vs GitHub Flow vs trunk-based) y qué encaja con PRs generados por agentes.
2. Protección de rama / evitar colisiones entre PRs paralelos (rulesets, CODEOWNERS, firma de commits, merge queues, stacked PRs, pre-commit, conventional commits + release automation).
3. Elección de forge (GitHub vs GitLab vs Gitea/Forgejo) para este caso de uso.
4. Estándares de CI/CD y despliegue para setups self-hosted pequeños y apps genéricas.
5. Métricas DORA y efecto de agentes IA sobre ellas.

## 2. Descartado y por qué

| Opción | Por qué se descarta para este caso |
|---|---|
| GitFlow (develop/release/hotfix branches) | El propio creador, Vincent Driessen, recomienda no usarlo para software desplegado continuamente desde 2020: "If your team is doing continuous delivery of software, I would suggest to adopt a much simpler workflow (like GitHub flow)" — [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/). Con múltiples PRs paralelos de agentes, la sobrecarga de ramas `develop`/`release` añade puntos de fusión y de deriva que ya son un problema sin agentes. Válido solo si hay que mantener varias versiones en producción a la vez (librerías, software versionado explícitamente), que no es el caso aquí. |
| Kubernetes/k3s como estándar por defecto para el servidor doméstico | Para <10 servicios en 1-2 nodos es sobreingeniería: "For a hobbyist homelab with 2–3 machines? Kubernetes is probably overengineering" — [terminalbytes.com](https://terminalbytes.com/kubernetes-at-home-from-docker-compose-to-k3s/); regla práctica citada: empezar con Docker Compose y migrar a k3s solo pasando de ~5 servicios con necesidad de service discovery — [fosslinux.com](https://www.fosslinux.com/158174/kubernetes-at-home-k3s-on-a-single-linux-server.htm). Se descarta como *default*, no como opción futura si el servidor crece a varios nodos.
| Argo CD / Flux (GitOps) como estándar por defecto en esta escala | Ambos asumen un cluster Kubernetes como target — [northflank.com](https://northflank.com/blog/flux-vs-argo-cd), [pipecd.dev](https://pipecd.dev/blog/2026/07/04/argo-cd-vs-flux-cd-vs-pipecd-choosing-the-right-gitops-tool/). Sin k3s de base no hay GitOps "de verdad" que aplique; para Compose en un solo host, el patrón equivalente es push-deploy simple (SSH + `docker compose up -d`) o un webhook, no un controlador de reconciliación. |
| HashiCorp Vault | BSL 1.1 desde 2023, no es código abierto puro y restringe ofrecerlo como servicio — [lalatenduswain / Medium](https://lalatenduswain.medium.com/openbao-vs-hashicorp-vault-the-secrets-management-showdown-every-devops-team-needs-to-read-in-2026-458ae0d9a408). Para este caso (self-hosted, sin necesidad de multi-tenancy empresarial) es más operación de la necesaria: "below that bar, a managed secret store plus OIDC in CI gives you most of the security benefit with none of the unseal-and-HA operational burden" — [unixy.io](https://unixy.io/blog/secrets-management-2026/). Se descarta Vault; OpenBao (fork MPL 2.0) queda como alternativa si algún día hace falta credenciales dinámicas de corta vida.
| Firma de commits (`required_signatures`) como gate único de confianza para PRs de agentes | GitHub Apps no tienen clave GPG/SSH propia, por lo que sus commits no se pueden firmar salvo re-firmado explícito; un ruleset de firma obligatoria bloquea todo PR de agente por defecto — [tenki.cloud](https://tenki.cloud/blog/copilot-commit-signing-code-review). Además "Verified" certifica autoría, no calidad: no sustituye revisión humana. Se descarta como control suficiente, se mantiene como control de *procedencia*, no de *corrección*.
| Merge queue nativo de GitHub como solución universal | Solo cubre bien equipos <10 ingenieros en un solo repo con CI simple; sin batching avanzado, sin prioridades, sin soporte de monorepo — [graphite.com](https://graphite.com/guides/merge-queue-comparison-github-gitlab-graphite). Válido como punto de partida, no como techo si el volumen de PRs de agentes crece mucho.
| GitLab CE self-managed como forge por defecto | Mayor madurez de CI (DAG pipelines, multi-project pipelines) — [devhandbook.io](https://devhandbook.io/blog/2026-08-18-self-hosted-git-gitea-forgejo-gitlab/) — pero consumo de recursos y complejidad operativa mucho mayores que Gitea/Forgejo para un servidor doméstico; se descarta por peso, no por capacidad.
| Reddit como fuente | Excluido explícitamente por las reglas de la tarea. |

## 3. Análisis

### 3.1 Branching: qué dice la evidencia

| Modelo | Evidencia primaria | Corroboración independiente | Tipo | Ajuste a PRs de agentes en paralelo |
|---|---|---|---|---|
| Trunk-based development (TBD) | DORA/Accelerate: "teams perform better when developers merge their work into trunk at least daily" y define TBD como <3 ramas activas, vida de rama <1 día — [dora.dev/capabilities/trunk-based-development](https://dora.dev/capabilities/trunk-based-development/); TBD es la práctica requerida para Continuous Integration en el modelo DORA — [dora.dev/capabilities/continuous-integration](https://dora.dev/capabilities/continuous-integration/) | trunkbaseddevelopment.com (guía de referencia de la industria, independiente de Google): ramas de corta vida "should only last a couple of days" y no compartidas entre desarrolladores — [trunkbaseddevelopment.com/short-lived-feature-branches](https://trunkbaseddevelopment.com/short-lived-feature-branches/) | Investigación académica/industrial (DORA) + guía de práctica consolidada | Alto: PRs de agente = rama corta, un solo "autor", vida de horas — es el caso de uso ideal para TBD con feature flags si el trabajo es incremental. |
| GitHub Flow | Recomendado explícitamente por el propio autor de GitFlow como sustituto para entrega continua — [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/) | Guías de la industria lo describen como adecuado para "continuous web deploys" — [codewithmukesh.com](https://codewithmukesh.com/blog/git-workflows-gitflow-vs-github-flow-vs-trunk-based-development/) (fuente secundaria, no vendor-neutral verificada a fondo) | Guía oficial de GitHub + reconocimiento de autor original | Alto: es esencialmente TBD con un paso extra de PR obligatorio — encaja de forma natural, porque cada agente ya trabaja vía PR. |
| GitFlow | Nota del propio autor (marzo 2020) desaconsejándolo para software de entrega continua, reservándolo para software "explícitamente versionado" — [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/) | Múltiples guías 2026 lo etiquetan como "legacy niche" (blogs de práctica, no fuente primaria) | Práctica de autor + consenso de blogs (baja independencia real, muchos repiten la misma cita) | Bajo: `develop`/`release`/`hotfix` añaden puntos de conflicto justo donde el problema ya es "muchos PRs paralelos"; sin necesidad de versiones múltiples en producción, no aporta nada. |

**Conclusión de branching:** trunk-based development (rama corta por issue/PR de agente, mergeada a `main` en <1 día, protegida por CI) es el estándar respaldado por DORA para maximizar rendimiento de entrega, y es el que mejor encaja estructuralmente con "muchos PRs de agentes en paralelo": cuanto más corta la rama, menor la ventana de colisión entre agentes. GitHub Flow es la instanciación práctica de TBD + PR obligatorio, que es exactamente lo que ya usa el sistema (issues → PR).

### 3.2 Protección de rama, evitar colisiones, automatización de release

| Mecanismo | Qué es | Estándar / mejor práctica | Fuente | Confianza |
|---|---|---|---|---|
| Rulesets vs Branch Protection Rules (GitHub) | Rulesets: evaluación agregada de múltiples reglas, ámbito organizativo, estado "Evaluate" antes de aplicar, visibles a cualquiera con acceso de lectura | Rulesets es la vía recomendada hoy para necesidades de más de un repo o enforcement fino; branch protection clásica sigue funcionando para un solo repo simple | Docs oficiales de GitHub — [docs.github.com/rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets); comparativas de práctica — [xeradi.dev](https://www.xeradi.dev/blog/github-branch-rulesets-guide) | Alta (doc oficial + práctica) |
| CODEOWNERS | Asigna revisores obligatorios por ruta | Con agentes autor de 30-50% de commits, el modelo clásico "se rompe": hace falta enrutar CODEOWNERS a revisores humanos específicos para rutas sensibles (CI/workflows, infra/IAM, auth/crypto, dependencias) con aprobación obligatoria | Práctica reportada (blogs/knowledge base, no doc oficial de GitHub sobre agentes) — [crashoverride.com](https://crashoverride.com/resources/knowledge-base/code-ownership/attributing-ai-commits-git) | Media (informe de práctica, sin estudio cuantitativo) |
| Firma de commits | Verifica autoría criptográfica | Útil como control de procedencia (saber qué proceso/bot generó el commit), **no** sustituye revisión de calidad; GitHub Apps no pueden firmar de forma nativa, lo que rompe gates que antes dependían solo de la firma | Práctica/blog de seguridad — [tenki.cloud](https://tenki.cloud/blog/copilot-commit-signing-code-review) | Media |
| Merge queue (GitHub) | Serializa merges probando cada PR contra el estado acumulado antes de fusionar | Gratis, nativo, adecuado para equipos <10 devs en un repo con CI simple; sin batching avanzado ni prioridades | Comparativa de vendor (Graphite, con interés comercial, pero describe también su propio producto con matices) — [graphite.com/guides/merge-queue-comparison](https://graphite.com/guides/merge-queue-comparison-github-gitlab-graphite) | Media (fuente con sesgo comercial pero técnicamente verificable) |
| Merge trains (GitLab) | Cada MR obtiene una ref temporal con el estado acumulado de MRs previos, pipelines en paralelo | Función madura desde GitLab 12.x, semi-linear history, re-arranca pipelines si un MR falla | Doc/dirección oficial de GitLab — [about.gitlab.com/direction/verify/merge_trains](https://about.gitlab.com/direction/verify/merge_trains/) | Alta (doc oficial) |
| Mergify | Merge queue de terceros con reglas de condiciones, útil para monorepos y regulados | "Best for teams that have outgrown GitHub's queue" | Vendor (mergify.com) — sesgo comercial, sin independiente que lo confirme en esta pasada | Baja-media (fuente única, vendor) |
| Stacked PRs (Graphite, y ahora GitHub nativo en preview 2026) | Descompone un feature grande en varios PRs pequeños y encadenados | PRs 200-400 líneas → 40% menos defectos que PRs grandes; PRs <200 líneas se aprueban 3× más rápido (cifras citadas repetidamente en blogs de práctica, sin cita a estudio original localizado) | InfoQ sobre lanzamiento de GitHub Stacked PRs — [infoq.com](https://www.infoq.com/news/2026/04/github-stacked-prs/); guía de Graphite (vendor) — [graphite.com/guides/stacked-diffs](https://graphite.com/guides/stacked-diffs) | Media: el patrón (PR pequeño = mejor revisión) tiene respaldo indirecto de Google ("PRs >400 líneas reducen calidad de revisión", citado en búsquedas de branching) pero la cifra exacta "40%/3×" no tiene fuente primaria verificada aquí — **marcar como sin verificar la cifra exacta**. |
| pre-commit (pre-commit.com) | Framework multi-lenguaje de hooks de git | Estándar de facto para checks locales rápidos (lint, formato, YAML, secretos) antes de CI; explícitamente **no sustituye** CI: "every security check that matters must also run in CI, on infrastructure the developer does not control" | Repo oficial — [github.com/pre-commit/pre-commit](https://github.com/pre-commit/pre-commit) (15.593★, activo, último push 2026-08-17 vía `gh api`); guía de práctica — [advancingengineering.dev](https://www.advancingengineering.dev/posts/2026-04-pre-commit-hooks/) | Alta (repo oficial activo + práctica consistente) |
| Conventional Commits + semantic-release / release-please | Automatiza versionado semántico y changelog a partir de mensajes de commit estructurados | semantic-release: release inmediato en cada push a main que cumpla el formato (24.069★, activo 2026-09-22 vía `gh api`); release-please: PR de release acumulativo que el humano aprueba y fusiona (7.550★, activo 2026-09-14 vía `gh api`) — ambos vivos y mantenidos | Repos oficiales; comparativa — [oleksiipopov.com](https://oleksiipopov.com/blog/npm-release-automation/) | Alta (repos activos verificados + patrón ampliamente documentado) |

**Para el caso concreto (muchos PRs de agentes en paralelo):** el mecanismo de colisión más relevante no es solo branch protection sino la combinación (a) rama corta por issue, (b) CI obligatorio + merge queue para serializar integraciones contra `main` cambiante, y (c) CODEOWNERS con revisión humana obligatoria en rutas sensibles (CI config, IaC, auth). Esto es "estándar" (a) y (b), y "mejor práctica emergente, no estándar aún consolidado" (c) — la industria todavía está adaptando CODEOWNERS a autoría mayoritariamente de agentes, sin un patrón único dominante.

### 3.3 Elección de forge

| Forge | Cuota/adopción | CI nativo | Runners self-hosted | Coste | Fuente |
|---|---|---|---|---|---|
| GitHub | 81,1% de desarrolladores profesionales lo usan (encuesta), 67,8% de cuota de plataformas VCS en general, más deseado (59,3%) y admirado (75,8%) | GitHub Actions | Self-hosted runners soportados, pero **desaconsejados en repos públicos** por riesgo de PRs de forks ejecutando código arbitrario en el runner — [github docs / secure-use](https://docs.github.com/en/actions/reference/security/secure-use); consenso práctico: "should be avoided entirely on public repositories" — [latchkey.dev](https://latchkey.dev/learn/ci-how-to/secure-self-hosted-runner-public-repo-github-actions) | Gratis para repos públicos y runners propios; Actions-minutos de pago en repos privados con runners hosted | Stack Overflow Developer Survey 2025 — [survey.stackoverflow.co/2025](https://survey.stackoverflow.co/2025/) |
| GitLab | 35,6% de uso profesional, 22% deseado, 42,1% admirado; fuerte en entornos corporativos/gubernamentales | GitLab CI (`.gitlab-ci.yml`), más maduro: DAG pipelines, parent-child, multi-project | Runners propios de primera clase | CE gratis self-managed; EE de pago | Stack Overflow Developer Survey 2025 (mismo informe) |
| Gitea | 58.152★, activo (último push 2026-09-24 vía `gh api`), MIT + edición comercial | Gitea Actions, compatible con sintaxis de GitHub Actions | Self-hosted por naturaleza | Gratis, ligero, ideal para 1 servidor doméstico | `gh api repos/go-gitea/gitea` (dato verificado en vivo) |
| Forgejo | Fork "duro" desde 2024, gobernanza sin ánimo de lucro (Codeberg), GPLv3+ | Forgejo Actions, compatible con sintaxis de workflows de GitHub Actions pero **no garantiza compatibilidad plena**: "some minimal tweaking will most likely be necessary" | Mismo modelo `act_runner`, self-hosted | Gratis; sin repo espejo en github.com para verificar estrellas vía `gh api` (aloja en Codeberg) | [forgejo.org/compare-to-gitea](https://forgejo.org/compare-to-gitea/); [forgejo.org/docs/latest/user/actions/overview](https://forgejo.org/docs/latest/user/actions/overview/) |

**Recomendación de forge para este caso:** con despliegue self-hosted en servidor doméstico y necesidad de correr agentes/CI sin depender de un tercero, **Gitea o Forgejo** son la opción "de facto" para forge autoalojado ligero (confirmado con datos en vivo: Gitea con 58k★ y actividad diaria); GitHub sigue siendo el estándar de la industria en general (81% de adopción) y su Actions/Copilot coding agent es lo mejor documentado para flujos de agentes IA, pero implica no-self-hosted del repo en sí (o Enterprise de pago) si se quiere mantener todo local. Si el sistema debe ser genérico y portable, conviene diseñar los workflows en sintaxis de GitHub Actions (el mayor común denominador: Forgejo Actions y Gitea Actions lo soportan con ajustes menores), evitando lock-in a features exclusivas de GitLab CI.

### 3.4 CI/CD y despliegue: qué es estándar vs exceso a esta escala

| Práctica | Estándar / Exceso | Evidencia | Confianza |
|---|---|---|---|
| GitHub Actions/GitLab CI con reusable workflows, environments con aprobación manual para producción | Estándar | Docs oficiales ampliamente adoptadas (no se cita URL específica adicional; patrón universalmente documentado en la doc oficial de cada plataforma) | Alta (inferencia sobre doc oficial, patrón muy estable) |
| Docker Compose como base de despliegue en servidor doméstico | Estándar a esta escala | "Start with Docker Compose... migrate to k3s [cuando] managing more than five services" — [terminalbytes.com](https://terminalbytes.com/kubernetes-at-home-from-docker-compose-to-k3s/); volúmenes simples en NAS único más apropiados que PV/PVC de k8s — mismo artículo | Media (fuente única de blog de práctica, pero consistente con literatura general de "boring technology") |
| k3s | Exceso salvo >5-10 servicios o >3-4 nodos | Mismo artículo; k3s en idle ~400MB RAM | Media |
| GitOps (Argo CD/Flux) en un solo host Compose | Exceso — GitOps asume reconciliación continua sobre manifiestos declarativos en un cluster; sobre un solo host Compose el patrón equivalente y suficiente es push-deploy vía SSH/webhook tras CI verde | Comparativas Argo CD/Flux asumen Kubernetes — [northflank.com](https://northflank.com/blog/flux-vs-argo-cd) | Media (inferencia razonada, no hay fuente que diga explícitamente "no usar GitOps sin k8s", pero se deduce de que ambas herramientas son controladores de Kubernetes) |
| Preview/ephemeral environments por PR | Estándar en SaaS/Kubernetes, exceso probable para home-server con recursos limitados: "aggressive teardown... destroy the environment the moment the PR merges" y patrones de BD por PR (snapshot, DB throwaway) añaden complejidad — [qovery.com](https://www.qovery.com/blog/per-pull-request-ephemeral-kubernetes-environments-tools-compared) | Con muchos PRs de agentes en paralelo, sí hay valor real (verificar cada PR de forma aislada antes de mergear), pero requiere automatización de teardown para no agotar recursos del servidor doméstico | Media |
| Secrets: OIDC para nubes, SOPS para configuración en Git, Vault/OpenBao para credenciales dinámicas | Estándar por capas: OIDC es "best practice 2026" para credenciales de nube desde CI — [docs.github.com OIDC](https://docs.github.com/enterprise-cloud@latest/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect); SOPS adecuado si secretos viven cifrados en Git junto a manifiestos — [unixy.io](https://unixy.io/blog/secrets-management-2026/); Vault/OpenBao solo si hace falta credenciales de corta vida dinámicas, exceso si no | Alta para OIDC (doc oficial + consenso), media para SOPS/Vault (blogs de práctica) |
| Observabilidad (Prometheus/Grafana) | Básico recomendable pero no crítico a esta escala; sin fuente específica consultada en esta pasada — **sin verificar en detalle**, se marca como pendiente | — | Baja (no investigado a fondo, inferencia general) |
| Runners self-hosted para CI de PRs de agentes en repos privados | Razonablemente seguro si el repo es privado y los "forks" son en realidad ramas del propio bot con permisos controlados; sigue el mismo riesgo de ejecución arbitraria si el agente puede escribir workflows — mitigación: ephemeral runners, runner groups por nivel de confianza, no auto-ejecutar workflows tras push de agente sin aprobación humana (patrón usado por Copilot coding agent: "Actions workflows do not run automatically when Copilot pushes changes... a maintainer... has to press Approve and run workflows") | [docs.github.com secure-use](https://docs.github.com/en/actions/reference/security/secure-use); comportamiento de Copilot coding agent — [github.blog](https://github.blog/ai-and-ml/github-copilot/from-idea-to-pr-a-guide-to-github-copilots-agentic-workflows/) | Alta (doc oficial + comportamiento de producto documentado) |

### 3.5 Incidente de referencia: supply chain en Actions (por qué runners/Actions de terceros son un riesgo real, no teórico)

`tj-actions/changed-files` (usada por >23.000 repos) fue comprometida en marzo de 2025 (CVE-2025-30066): un token robado permitió reescribir tags de la Action para volcar secretos del runner en los logs de build — [wiz.io](https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066), [cisa.gov](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction). Corroborado independientemente por Unit42 (Palo Alto) — [unit42.paloaltonetworks.com](https://unit42.paloaltonetworks.com/github-actions-supply-chain-attack/) y StepSecurity — [stepsecurity.io](https://www.stepsecurity.io/blog/harden-runner-detection-tj-actions-changed-files-action-is-compromised/). **Confianza alta** (múltiples fuentes independientes: vendor de seguridad, agencia gubernamental CISA, otro vendor). Implicación directa para el proyecto: pin de Actions de terceros por SHA (no por tag), mínimo de permisos (`permissions:` explícito por workflow), y nunca ejecutar workflows de un PR de agente sin aprobación si ese PR puede tocar `.github/workflows/`.

### 3.6 Métricas DORA y efecto de agentes IA

- Las "cuatro claves" clásicas: deployment frequency, lead time for changes, change failure rate, y (desde 2023) failed deployment recovery time (antes MTTR) — [dora.dev/guides/dora-metrics](https://dora.dev/guides/dora-metrics/), historial oficial — [dora.dev/insights/dora-metrics-history](https://dora.dev/insights/dora-metrics-history/).
- En 2024 DORA reorganizó el modelo en **throughput** (lead time, deployment frequency, failed deployment recovery time) e **instability** (change failure rate + nueva **deployment rework rate**, quinta métrica) — mismo enlace de historial.
- **DORA 2025 — "State of AI-assisted Software Development"** (informe primario, ~5.000 profesionales, >100h de datos cualitativos): 90% de encuestados usa IA en el trabajo (+14 puntos interanual), >80% cree que aumentó su productividad, pero 30% declara poca o ninguna confianza en el código generado por IA — [dora.dev/dora-report-2025](https://dora.dev/dora-report-2025/), resumen — [scrum.org](https://www.scrum.org/resources/blog/dora-report-2025-summary-state-ai-assisted-software-development), anuncio oficial Google Cloud — [cloud.google.com/blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report).
- **Hallazgo central, cita textual del informe**: "Unlike last year, we observe a positive relationship between AI adoption on both software delivery throughput and product performance... However, AI adoption does continue to have a negative relationship with software delivery stability." — recogido en [cloud.google.com/blog](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report). Es decir: **la IA aumenta el throughput pero sigue penalizando la estabilidad** (change failure rate/rework), tendencia consistente respecto a informes anteriores de DORA sobre IA.
- Marco "amplificador": "AI doesn't fix a team; it amplifies what's already there" — mismo informe. Implicación directa para el proyecto: sin CI robusto, tests obligatorios y revisión humana en rutas sensibles, más PRs de agentes en paralelo = más throughput aparente pero más inestabilidad real.
- **Octoverse 2025** (GitHub, informe de vendor pero con datos propios de la plataforma, no encuesta): el Copilot coding agent generó >1 millón de PRs en 5 meses (mayo-sept 2025); comentarios en commits cayeron 27% mientras los PRs subieron 20% — señal de que la revisión "de verdad" podría estar diluyéndose frente al volumen — [github.blog/octoverse](https://github.blog/news-insights/octoverse/what-986-million-code-pushes-say-about-the-developer-workflow-in-2025/). **Confianza media**: es fuente única (vendor, aunque con datos de telemetría propia verificables en la práctica), sin corroboración independiente de la cifra de comentarios/PR en esta pasada.
- Refuerzo práctico (post oficial de GitHub, no encuesta pero con cifra propia de producto): "más de 1 de cada 5 code reviews en GitHub ahora involucra a un agente"; Copilot code review superó 60 millones de revisiones, creciendo 10× en menos de un año — [github.blog](https://github.blog/ai-and-ml/generative-ai/agent-pull-requests-are-everywhere-heres-how-to-review-them/). **Confianza media** (vendor claim, sin fuente independiente).

### 3.7 Dónde la hipótesis del usuario no se sostiene

**Nota de alcance:** el contexto inicial del proyecto (Claude planifica → DeepSeek implementa como PRs, "muchos PRs en paralelo", git/GitFlow, self-hosted, GitHub/GitLab) fue presentado como ideas de partida del usuario, no como decisiones cerradas. Aplicando la evidencia de este front punto por punto:

| Hipótesis del usuario | ¿Se sostiene? | Evidencia | Fuente |
|---|---|---|---|
| **GitFlow** como modelo de branching | **No se sostiene.** El propio creador la desaconseja para entrega continua desde 2020; DORA correlaciona alto rendimiento con trunk-based, no con GitFlow. Con múltiples agentes escribiendo PRs en paralelo, `develop`/`release`/`hotfix` añaden puntos de fusión justo donde ya hay riesgo de colisión. | Ver §2 y §3.1 | [nvie.com](https://nvie.com/posts/a-successful-git-branching-model/), [dora.dev/capabilities/trunk-based-development](https://dora.dev/capabilities/trunk-based-development/) |
| **Self-hosting** (servidor doméstico) como plataforma de CI/CD | **Se sostiene solo con matices de aislamiento.** Es viable y económicamente razonable (no hay presión de escala que lo desaconseje), pero self-hosting implica que el propio runner de CI vive en la máquina del usuario: si un PR de agente puede modificar `.github/workflows/` (o equivalente) y el runner no es efímero/aislado, el riesgo es estructuralmente el mismo que el de un fork no confiable en un repo público — ya materializado en el incidente real tj-actions/changed-files (CVE-2025-30066, marzo 2025). La hipótesis "self-host sin más" no se sostiene; "self-host con runners efímeros, permisos mínimos y aprobación manual antes de ejecutar workflows tocados por un agente" sí. | Ver §3.5 | [docs.github.com/secure-use](https://docs.github.com/en/actions/reference/security/secure-use), [wiz.io](https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066), [cisa.gov](https://www.cisa.gov/news-events/alerts/2025/03/18/supply-chain-compromise-third-party-tj-actionschanged-files-cve-2025-30066-and-reviewdogaction) |
| **"Muchos PRs de agentes en paralelo"** como diseño de partida (asumir volumen alto desde el día 1) | **No se sostiene sin condición previa.** El hallazgo central de DORA 2025 es que la IA "amplifica lo que ya existe": aumenta el throughput pero penaliza la estabilidad — y esto se observa incluso en GitHub a escala masiva, donde los comentarios en commits cayeron 27% mientras los PRs subieron 20% (la revisión real no escala al mismo ritmo que el volumen). Para un setup nuevo, sin CI robusto ni capacidad de revisión humana ya probada, diseñar para "muchos PRs en paralelo" desde el inicio es diseñar para amplificar inestabilidad antes de haber demostrado que el proceso de revisión aguanta. Recomendación: construir primero el camino estrecho (TBD + CI obligatorio + revisión humana en rutas sensibles) con paralelismo bajo, y escalar el número de agentes concurrentes solo cuando el change failure rate se mantenga bajo control. | Ver §3.6 | [cloud.google.com/blog DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report), [github.blog/octoverse](https://github.com/news-insights/octoverse/what-986-million-code-pushes-say-about-the-developer-workflow-in-2025/) |
| **GitHub o GitLab** como forge asumido | **No se sostiene como elección obligatoria**, dado que el propio contexto pide self-hosted. Gitea/Forgejo cubren el caso de uso self-hosted con sintaxis de workflows compatible con GitHub Actions, gratis, y con actividad verificada en vivo (Gitea: 58.152★, último push 2026-09-24 vía `gh api`). La ventaja real de GitHub/GitLab aquí no es arquitectónica sino de madurez de tooling para agentes (Copilot coding agent, revisión automática, audit log de Enterprise Cloud) — un argumento de conveniencia, no de necesidad. Si el usuario prioriza self-hosting real y no depender de un tercero, Gitea/Forgejo es la opción más coherente con su propia premisa. | Ver §3.3 | [go-gitea/gitea (gh api)](https://github.com/go-gitea/gitea), [forgejo.org/compare-to-gitea](https://forgejo.org/compare-to-gitea/) |

En conjunto: de las cuatro hipótesis iniciales, una (GitFlow) queda descartada sin ambigüedad por la evidencia, dos (self-hosting, forge GitHub/GitLab) se sostienen solo parcialmente o dejan de ser obligatorias una vez que se examinan las alternativas self-hosted, y una (paralelismo alto desde el inicio) es la más arriesgada de las cuatro porque es precisamente el escenario donde la propia investigación primaria (DORA 2025) predice el peor resultado si no se resuelve antes la capacidad de revisión.

### 3.8 Trazabilidad: quién hizo qué (identidad por agente, trailers, firma, logs de auditoría)

Con múltiples agentes IA generando PRs, el requisito no es solo "¿pasa el CI?" sino "¿quién (qué agente, qué ejecución, sobre qué issue) generó este cambio, y quién lo aprobó?". Mecanismos disponibles hoy, de menor a mayor garantía:

| Mecanismo | Qué aporta | Nivel de garantía | Fuente |
|---|---|---|---|
| **Identidad diferenciada por agente** (bot account o GitHub App dedicada por tipo de agente, no un token compartido) | Cada PR/commit queda atribuido en la UI y en `git log` a un actor propio (p. ej. `deepseek-agent[bot]`), no a una cuenta humana ni a un token genérico. Precedente ya en producción: el Copilot coding agent crea su propia rama con nombre identificable (`copilot/add-...`) y todos sus commits/sesión quedan visibles y trazables como acción del agente, no del humano que lo invocó. | Trazabilidad de *autoría de superficie* (qué cuenta hizo el push), no de *proceso* | [github.blog/copilot-agentic-workflows](https://github.blog/ai-and-ml/github-copilot/from-idea-to-pr-a-guide-to-github-copilots-agentic-workflows/) |
| **Trailers de commit estructurados** (`Generated-by: deepseek-agent`, `Agent-Run-Id: <uuid>`, `Issue: #123`, o `Co-authored-by:` para el agente) | Vincula cada commit a la ejecución concreta del agente y al issue que lo originó, consultable con `git log --grep`/`git blame` sin depender de la API del forge | Trazabilidad de *contexto* (qué tarea, qué ejecución), complementa (no sustituye) la identidad de actor | Recomendado como práctica en gestión de atribución de commits de IA — [crashoverride.com](https://crashoverride.com/resources/knowledge-base/code-ownership/attributing-ai-commits-git) |
| **Firma de commits — con matiz importante**: la firma GPG/SSH clásica no la pueden usar GitHub Apps (no tienen clave propia), lo que rompe cualquier gate basado solo en "Verified" para PRs de agente | La alternativa correcta es **firma keyless con Sigstore/gitsign**: un certificado efímero se emite ligado a una identidad OIDC (la del job de CI, no una clave estática de larga vida), y cada firma queda registrada en el log de transparencia público **Rekor**, con marca de tiempo verificable — esto sí resuelve el problema de "GitHub App sin clave" porque la identidad la aporta el proveedor OIDC del pipeline (GitHub Actions, GitLab CI y Forgejo Actions emiten tokens OIDC a sus jobs), no una clave que la App tendría que custodiar | Trazabilidad de *procedencia criptográfica* (quién/qué pipeline firmó, cuándo, con prueba pública inmutable) — es la garantía más fuerte de las tres, pero certifica autoría, no corrección del código | [docs.sigstore.dev/cosign/signing/overview](https://docs.sigstore.dev/cosign/signing/overview/); limitación de la firma clásica para GitHub Apps — [tenki.cloud](https://tenki.cloud/blog/copilot-commit-signing-code-review) |
| **Audit log del forge** | En GitHub, el audit log de organización registra actor, acción y timestamp para fusiones, cambios de branch protection, instalación de Apps, etc., vía el calificador `actor:` y `action:`, con **retención de 180 días**; acceso por UI para cualquier org, y por API GraphQL/REST **solo en GitHub Enterprise Cloud** | Trazabilidad *administrativa* de quién aprobó/fusionó/cambió reglas — necesaria para reconstruir la cadena issue → PR de agente → revisión humana → merge | [docs.github.com — audit log de organización](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization) |

**Recomendación concreta para este proyecto:** (1) una identidad de bot/App distinta por tipo de agente (no un token compartido entre todos los agentes DeepSeek), con convención de nombre de rama `agent/<agente>/<issue-id>`; (2) trailer obligatorio `Generated-by:` + `Agent-Run-Id:` + referencia al issue en cada commit, validable por un hook de pre-commit o check de CI; (3) firma keyless vía gitsign donde el pipeline pueda obtener token OIDC (cubre GitHub Actions, GitLab CI y Forgejo Actions por igual, evitando el problema de gestión de claves estáticas); (4) exportación periódica del audit log del forge (o del log de actividad equivalente) correlacionada por `Agent-Run-Id` para poder responder, meses después, "qué agente tocó este archivo y quién lo aprobó" — esto es doblemente importante en un forge self-hosted (Gitea/Forgejo) porque, a diferencia de GitHub Enterprise Cloud, **no se ha verificado en esta investigación si su log de actividad de administrador ofrece la misma granularidad y retención que el audit log de GitHub**; queda como duda abierta (ver §6).

## 4. Estándar / lo mejor / exceso — resumen con procedencia y confianza

| Decisión | Estándar hoy | Lo mejor para este proyecto | Exceso a evitar | Confianza |
|---|---|---|---|---|
| Branching | Trunk-based / GitHub Flow (DORA + práctica de autor de GitFlow) | Rama corta por issue de agente, CI obligatorio, merge a `main` en <1 día | GitFlow con develop/release/hotfix | Alta — primaria DORA + declaración pública del autor original, 2 fuentes independientes de tipo distinto (estudio + práctica) |
| Protección de rama | Rulesets GitHub / merge queue | Rulesets + CI obligatorio + merge queue nativo (gratis) mientras el volumen de PRs sea manejable; escalar a Mergify solo si aparece cuello de botella | Firma de commits como único gate de confianza; Mergify/Graphite desde el día 1 sin necesidad probada | Media-alta — doc oficial para rulesets (alta), vendor claims para merge queue comparado (media) |
| Revisión de PRs de agentes | Emergente, no consolidado | Checklist explícito: CI/tests no debilitados, sin duplicación de utilidades, sanitización de input no confiable, permisos mínimos, aprobación humana en workflows/IaC/auth | Confiar en "Verified" (firma) como proxy de calidad | Media — un solo vendor post (GitHub), pero con cifras propias de telemetría consistentes con Octoverse |
| Forge | GitHub domina adopción general (81%); Gitea/Forgejo domina self-hosted ligero | Gitea o Forgejo self-hosted en el servidor doméstico, usando sintaxis de GitHub Actions como mayor común denominador para portabilidad | GitLab self-managed completo (más pesado de lo necesario) | Alta para cuota de mercado (encuesta SO 2025), alta para métricas de repo (datos en vivo vía `gh api`), media para elección recomendada (síntesis propia) |
| Runners CI | Self-hosted runners no deben tocar repos públicos ni ejecutar workflows de PRs de agentes sin aprobación | Runners self-hosted en repo privado + ephemeral + aprobación manual de "Approve and run workflows" en PRs de agente que tocan `.github/workflows/` | Runners persistentes no-ephemeral compartidos entre repos de distinta confianza | Alta — doc oficial GitHub + incidente real documentado (tj-actions) con 3+ fuentes independientes |
| Despliegue self-hosted | Docker Compose para <5 servicios en 1 host | Compose + push-deploy simple vía CI (SSH/webhook) | k3s + GitOps (Argo CD/Flux) sin necesidad de multi-nodo | Media — blogs de práctica, consistentes entre sí, sin estudio formal |
| Secretos | OIDC para nube, SOPS para config en Git | OIDC donde aplique (nube), SOPS para secretos versionados junto a Compose/manifiestos | Vault/HA para un solo servidor doméstico | Alta para OIDC (doc oficial), media para SOPS (blogs) |
| Métricas de éxito | DORA 4-5 claves | Medir deployment frequency y change failure rate desde el principio, vigilando el trade-off throughput/estabilidad que la propia DORA 2025 documenta en agentes IA | Ignorar change failure rate mientras se optimiza solo velocidad de PRs de agentes | Alta — informe primario DORA 2025, con Octoverse como corroboración independiente parcial (tipo de fuente distinto: encuesta vs telemetría de plataforma) |
| Trazabilidad "quién hizo qué" | Emergente, no consolidado como estándar único | Identidad de bot/App distinta por agente + trailers `Generated-by`/`Agent-Run-Id` + firma keyless (gitsign/Sigstore vía OIDC del pipeline) + audit log del forge correlacionado | Depender solo de "Verified" (firma clásica) como prueba de calidad, o de un token compartido entre todos los agentes sin diferenciar actor | Media — doc oficial para audit log de GitHub y para Sigstore (alta en esos dos puntos), pero el conjunto como receta integrada es síntesis propia sin un caso de referencia público verificado con múltiples agentes IA en producción |

## 6. Dudas abiertas

1. **Forgejo en Codeberg**: no se pudo aplicar `gh api` (solo funciona sobre github.com) para verificar estrellas/actividad de Forgejo de forma equivalente a Gitea. Falta ese dato duro; la comparación se apoya en fuentes secundarias (blogs 2026).
2. **Cifra "PRs 200-400 líneas → 40% menos defectos / <200 líneas se aprueban 3× más rápido"**: aparece repetida en varios blogs sobre stacked PRs pero no se localizó el estudio original (posiblemente basado en investigación de Google/Microsoft sobre tamaño de PR, no confirmada aquí). **Tratar como sin verificar** hasta encontrar la fuente primaria.
3. **CODEOWNERS con autoría mayoritaria de agentes**: no hay un patrón estándar consolidado, solo prácticas emergentes de blogs individuales — reevaluar en 6-12 meses cuando el ecosistema madure.
4. **Observabilidad para home server** (Prometheus/Grafana vs alternativas ligeras): no investigado en profundidad, pendiente de un pase adicional si se necesita para la decisión final.
5. **Coste real de Actions/CI en runners self-hosted a esta escala** (electricidad, mantenimiento del propio servidor doméstico vs minutos de GitHub-hosted): no cuantificado, solo cualitativo.
6. **Relación exacta entre change failure rate/deployment rework rate y volumen de PRs de agentes**: DORA 2025 da la relación cualitativa (throughput↑, estabilidad↓) pero no se localizó el desglose cuantitativo (porcentajes concretos) en el resumen accesible sin descargar el PDF completo del informe — si se necesita el número exacto, hay que leer el PDF completo en https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf.
7. **Log de auditoría/actividad de Gitea y Forgejo**: no se verificó si ofrece granularidad equivalente al audit log de GitHub (actor, acción, timestamp, retención, API consultable) — relevante porque la recomendación de forge self-hosted (§3.3, §3.7) depende en parte de poder correlacionar `Agent-Run-Id` con acciones del forge para trazabilidad completa.
8. **Identidad diferenciada por GitHub App** (o equivalente en Gitea/Forgejo) para cada tipo de agente: no se verificó con doc oficial (404 en el intento de esta sesión) cómo se refleja exactamente en `git log`/API la distinción entre distintas Apps/bots; la recomendación de §3.8 se apoya en el comportamiento observado de un solo caso (Copilot coding agent), no en documentación general de la plataforma.
9. **Gitsign/Sigstore en la práctica con múltiples agentes IA concurrentes**: no se encontró un caso de referencia público que combine gitsign + trailers + audit log específicamente para flujos de agentes IA generando PRs en paralelo; la receta de §3.8 es síntesis propia (inferencia) a partir de piezas verificadas por separado, no un patrón ya validado en producción para este escenario exacto.
