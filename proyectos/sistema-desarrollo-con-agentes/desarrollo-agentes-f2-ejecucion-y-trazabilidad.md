Cómo pasa el trabajo de tarea a PR mergeada con agentes, cómo se orquesta, qué datos hay de revisión y merge, y cómo se sabe quién hizo qué.

Informe de un frente. La síntesis, con las decisiones pendientes, está en [[desarrollo-agentes-investigacion]].

Fecha de investigación: 2026-09-24. Estado de "current" verificado con búsquedas de 2026 (no memoria de entrenamiento).

**Nota sobre el encargo**: el planteamiento inicial (Claude produce issues, DeepSeek los implementa vía flujo issue→PR) se trata aquí como **hipótesis a contrastar, no como decisión tomada**. Este informe compara ese patrón con las alternativas reales que usa la comunidad (sesión única local con worktrees, plan-then-execute en una sola sesión larga, agentes cloud/background) y evalúa con evidencia si conviene o no usar un modelo más barato de otro vendor para implementar, frente a un setup de un solo vendor. La sección 5 recoge explícitamente dónde la evidencia contradice o matiza la hipótesis de partida.

## 1. Pregunta

Para un sistema de desarrollo genérico donde Claude (vía Claude Code, Pro) convierte ideas en casos de uso e issues, y potencialmente un modelo más barato (p. ej. DeepSeek, API oficial) implementa esos issues como código+tests con Git+PR+CI/CD+DevSecOps: ¿qué sistemas reales convierten issues en PRs mergeadas con agentes, cómo se orquesta trabajo de muchos agentes en la práctica, qué hace un issue "implementable" por un agente, cómo funciona (y cuánto cuesta en revisión humana) el ciclo de revisión de esos PRs, y — la pregunta que realmente hay que responder antes de construir nada — ¿es issue→PR con dos vendors distintos la mejor forma de ejecutar esto, o hay patrones con más evidencia a favor? Se busca separar estándar de facto, lo mejor por evidencia, y hype.

## 2. Descartado y por qué

- **Búsqueda exhaustiva de precios exactos actuales de Copilot coding agent (premium requests) y de Cursor background agents**: se agotó el presupuesto de `WebSearch` de la sesión (200/200) antes de poder verificar cifras de precio puntuales de 2026 para estos dos. Se reporta lo encontrado hasta ese punto y se marca el resto "sin verificar".
- **Devin, Jules, Cursor background agents como candidatos a ejecutar DeepSeek**: descartados como ejecutores del modelo barato porque son cerrados, cloud-only, atados a su propio modelo/orquestador (Devin: modelo propio de Cognition; Jules: Gemini; Cursor background agents: modelos de Cursor con BYOK solo para claves, no para sustituir el agente entero). No aportan la pieza "DeepSeek implementa" del sistema propuesto.
- **GitHub Copilot coding agent y OpenAI Codex cloud como ejecutores de DeepSeek**: descartados por la misma razón — el "coding agent" nativo de GitHub solo permite elegir entre modelos Claude o modelos OpenAI/Codex para la tarea de issue→PR (verificado en el changelog de selección de modelo), no modelos de terceros como DeepSeek. El BYOK de Copilot CLI/VS Code Chat es para *chat*, no para el coding agent cloud que resuelve issues.
- **anthropics/claude-code-action como ejecutor de DeepSeek**: descartado — es un wrapper de Claude Code, que ya se sabe (dato dado como cierto en el enunciado) no admite modelos no-Anthropic. Se mantiene en el análisis solo como patrón de referencia para el "front" de PR/CI, no como candidato de ejecución barata.
- **Gas Town / Beads como única solución de orquestación**: son proyectos de ~1 año (Beads creado oct-2025, Gas Town ene-2026), sin adopción corporativa documentada más allá de posts del propio autor y comunidad de early adopters; se tratan como señal de tendencia, no como estándar probado. Ver sección 4.
- **Vibe Kanban como plataforma con soporte comercial**: descartado como apuesta de producto — Bloop (la empresa) cerró y el proyecto pasó a mantenimiento comunitario open source el 10-abr-2026; sigue siendo útil como herramienta local (worktrees + kanban), pero no como servicio con SLA. [Anuncio](https://www.vibekanban.com/blog/shutdown)
- **Estudios de "AI-to-AI code review" y refactoring con AIDev**: mencionados pero no profundizados por límite de tiempo/búsquedas; quedan en "dudas abiertas".

**Estándar de facto (por adopción)**: el patrón **"asignar issue a un agente cloud del propio vendor de Git hosting → PR draft → CI gatea → revisión humana"** es el que domina, encabezado por GitHub Copilot coding agent (GA desde sep-2025, historia de producción de 10 meses documentada en dotnet/runtime) y replicado casi al pie de la letra por Codex Cloud, Jules y GitLab Duo. Evidencia: documentación oficial de los 4 vendors + reporte práctico de dotnet/runtime (ver 3.3). Confianza **alta**.

**Mejor para el caso de uso descrito (Claude planifica, DeepSeek implementa)**: de los evaluados, solo dos permiten sustituir el modelo ejecutor por DeepSeek de forma real: **OpenHands resolver** (open source, LiteLLM, autoalojable, cero fricción para DeepSeek) y **GitLab Duo Self-Hosted** (soporta DeepSeek Coder vía AI Gateway propio, pero solo si ya se usa GitLab y con más carga operativa de GPU). Para un stack ligero sobre GitHub, OpenHands resolver es la opción con más adopción real (89k★, 4 años de vida) y con la propiedad exacta que pide el enunciado. Confianza **alta** en la capacidad técnica (docs oficiales + issues del propio repo); **media** en "está probado en producción a esta escala" porque no se halló un caso público equivalente al de dotnet/runtime usando DeepSeek específicamente vía OpenHands — inferencia razonable, no verificada con un caso de uso real publicado.

Confianza **alta** (docs oficiales + métricas gh api).

**Hype / sin contrastar todavía**: Gas Town y, en menor medida, Beads. Ambos con crecimiento viral en estrellas pero con evidencia dominada por el propio autor (Yegge) y prensa técnica que cubre sus posts, sin estudios independientes de resultados en producción a fecha de esta investigación. Karpathy ha criticado explícitamente el discurso de "agent swarms" como prematuro/exagerado. [Cobertura Karpathy](https://eu.36kr.com/en/p/3747726516601353) — confianza **baja-media** en que estos patrones sean ya "lo mejor probado" frente a alternativas más simples (un HN post de 51 comentarios reemplazó Beads por un tracker Markdown más simple, señal de contra-evidencia práctica). ### 3.3 Diseño de issues para que un agente los implemente

Evidencia primaria oficial + evidencia práctica con números duros (caso dotnet/runtime, 10 meses / 878 PRs) coinciden en los mismos puntos:

| Factor | Guía oficial (GitHub Docs) | Evidencia práctica (dotnet/runtime, mayo-2025→marzo-2026) |
|---|---|---|
| Tamaño/alcance | Un issue = un resultado; tareas compuestas ("refactoriza X y añade Y y arregla Z") dan peor resultado que 3 issues separados. [Best practices](https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks) | Tareas de 1-50 líneas: 76-80% de éxito; 101-500 líneas: cae a 64%. |
| Criterios de aceptación | Deben ser explícitos y verificables ("reglas observables y comprobables", no "escribe código limpio"); sin ellos el agente optimiza volumen, no corrección. | Issues con reproducción clara y comportamiento esperado tuvieron éxito consistente; vagos → soluciones vagas. |
| Contexto del repo | `.github/copilot-instructions.md` con cómo construir/testear y convenciones. | Tasa de éxito subió de 38% → 69% tras documentar el repo en detalle; documentar patrones de testing/estilo/build evitó errores repetidos. |
| Tipo de tarea apto | Empezar por tests, docs, refactors simples, bugs acotados. | Mejor: eliminación/limpieza (84.7%), tests (75.6%), refactor (69.7%), bugs bien especificados (69.4%). Peor: optimización de performance (54.5%), C++ nativo, juicio arquitectónico. |
| Trayectoria de mejora | — | 41.7% (mayo) → ~71% (reciente) de éxito, atribuido a mejor documentación del repo, no a mejora del modelo. Cita literal del informe: *"preparation matters more than the model"*. |

Fuente primaria de esta tabla: [GitHub Docs — Best practices for using Copilot to work on tasks](https://docs.github.com/copilot/how-tos/agents/copilot-coding-agent/best-practices-for-using-copilot-to-work-on-tasks) y [devblogs.microsoft.com — Ten Months with CCA in dotnet/runtime](https://devblogs.microsoft.com/dotnet/ten-months-with-cca-in-dotnet-runtime/). Tipo de evidencia: (a) docs oficiales del vendor, (b) informe de práctica real con datos cuantitativos de un repo de gran visibilidad (dotnet/runtime, Microsoft). Corroboración independiente: 2 fuentes independientes coincidiendo en los mismos factores (tamaño, criterios de aceptación, contexto). Confianza: **alta**.

Guía de Anthropic para issues/tareas de agentes es más genérica (no específica de "escribir un issue"), centrada en: instrucciones concisas y concretas en `CLAUDE.md`, cercanía de la guía especializada a los ficheros que gobierna, y el agente committeando progreso a git + notas de progreso para tareas largas. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) — Tipo de evidencia: docs oficiales del vendor. Confianza **alta** en que es la postura oficial de Anthropic; **media** en que sea la mejor práctica *específica* para escribir issues (Anthropic no publica una guía de "cómo escribir un issue" comparable a la de GitHub).

No se halló guía oficial de OpenAI equivalente y explícita "cómo escribir un issue para Codex" — se apoya en `AGENTS.md` (convención de facto cross-vendor, adoptada también por Codex, Jules, gh-aw, etc.), pero no se verificó una página de mejores prácticas dedicada de OpenAI en esta sesión. **Sin verificar**.

Confianza **alta** — 3+ fuentes independientes, con datos cuantitativos coincidentes en dirección (aunque no en magnitud exacta) del mismo fenómeno.

### 3.5 Issue→PR (async/cloud) vs. alternativas: sesión única local, plan-then-execute, worktrees

La hipótesis de partida asume que "issue→PR" es *la* forma de ejecutar el trabajo. La evidencia recogida en 3.1-3.2 muestra en realidad **tres patrones distintos en uso real**, no uno:

| Patrón | Ejemplo real | Evidencia de que funciona | Evidencia de sus límites |
|---|---|---|---|
| **A. Issue→PR asíncrono, agente cloud del vendor** | GitHub Copilot coding agent, Codex Cloud, Jules, GitLab Duo | 878 PRs / 67.9% merge en dotnet/runtime a lo largo de 10 meses en producción real. [devblogs.microsoft.com](https://devblogs.microsoft.com/dotnet/ten-months-with-cca-in-dotnet-runtime/) | El propio informe: el cuello de botella se traslada a revisión (16.5 comentarios/PR); tareas que requieren juicio arquitectónico rinden peor (54.5% en optimización de performance); cuando dos agentes distintos tocan el mismo repo en solape temporal, conflicto de merge al 41.7% (vs 19.8% intra-agente). [AgenticFlict](https://arxiv.org/abs/2604.03551) |
| **B. Sesión local única, "plan-then-execute" en un solo hilo de contexto** (el modo por defecto de Claude Code / Codex CLI / Copilot CLI usado interactivamente) | Recomendación explícita de Cognition (creadores de Devin) tras operar Devin en producción: *"agentes lineales de un solo hilo"* para la mayoría de tareas, evitando el paralelismo de sub-agentes salvo compresión de contexto para tareas muy largas. [cognition.com/blog/dont-build-multi-agents](https://cognition.com/blog/dont-build-multi-agents) | Argumento y evidencia interna de Cognition (no es un estudio independiente, es vendor-claim, pero viene de la empresa que más ha operado un agente autónomo de codificación en producción) — señala un fallo estructural concreto: sub-agentes en paralelo sin compartir el *trace* completo toman decisiones implícitas conflictivas (ejemplo citado: un sub-agente construye un fondo de Super Mario cuando la tarea pedía Flappy Bird, y el resto de sub-agentes no puede reconciliarlo). | Es la postura de un solo vendor, sin contraste de un estudio académico independiente que compare directamente sesión única vs. multi-agente en el mismo conjunto de tareas — confianza **media**, no alta. |

**Lectura combinada**: la evidencia no dice "issue→PR es incorrecto"; dice que **issue→PR asíncrono es un buen patrón cuando las tareas están bien acotadas y el cuello de botella de revisión está gestionado** (caso dotnet/runtime, patrón A) — pero para el caso descrito en la hipótesis (Claude planificando y siendo la "inteligencia", con una sola cadena issue→implementación→PR por tarea, sin paralelismo masivo) el patrón real más próximo y con más respaldo de evidencia coincide en lo esencial con A: una tarea, un agente, un PR, revisado por un humano o por el modelo fuerte. Donde la hipótesis se queda corta es en no contemplar que **el patrón B (sesión única, sin pasar por un issue tracker intermedio en absoluto)** tiene defensores de peso (Cognition) precisamente para el tipo de tareas de tamaño medio que probablemente serán las más comunes en un backlog generado por Claude — y que forzar todo por un issue formal cuando una sesión directa de Claude Code + DeepSeek bastaría añade fricción sin evidencia de que compense. Ver sección 5.

### 3.6 ¿Conviene un modelo más barato de otro vendor para implementar, frente a un setup de un solo vendor?

Evidencia **a favor** de un modelo barato/no-Anthropic como implementador:
- Ahorro de coste evidente por diseño (ya asumido en el enunciado, no se re-investiga aquí).
- El hallazgo más sólido de todo este informe (dotnet/runtime, 3 fuentes independientes corroborando la misma dirección) es que **la preparación del issue pesa más que la capacidad del modelo**: 38%→69% de éxito solo por mejorar `copilot-instructions.md`, sin cambiar de modelo. Cita literal: *"preparation matters more than the model"*. Esto es evidencia real (no inferencia) de que invertir en cómo Claude escribe el issue puede compensar buena parte de la diferencia de capacidad entre un modelo caro y uno barato. [devblogs.microsoft.com](https://devblogs.microsoft.com/dotnet/ten-months-with-cca-in-dotnet-runtime/)
- OpenHands (soporte DeepSeek nativo vía LiteLLM) y GitLab Duo Self-Hosted (DeepSeek Coder documentado oficialmente) son herramientas reales, no experimentales, que ya asumen que el modelo de implementación es intercambiable — la industria no trata "un solo modelo para todo el pipeline" como un requisito.

Evidencia **en contra** / riesgo, no contemplada por la hipótesis original:
- El estudio "Where Do AI Coding Agents Fail" muestra una **varianza enorme de merge rate por agente** (Codex 82.59% vs. Copilot 43.04% vs. Devin 53.76%, mismo dataset, mismas condiciones de mercado) — el agente/modelo concreto sí importa mucho para el resultado final, no solo la calidad del issue. [arxiv.org/abs/2601.15195](https://arxiv.org/abs/2601.15195)
- El cuello de botella ya identificado (3.4) es la **revisión humana**, no la generación de código. Un modelo más barato que produzca PRs de menor calidad media desplaza más trabajo hacia ese cuello de botella ya saturado (16.5 comentarios/PR en el caso Copilot/dotnet), lo cual puede anular el ahorro de coste del modelo si se mide en coste total del sistema (tokens + tiempo de ingeniero senior revisando). **Esto es inferencia** (no hay un estudio que mida directamente "coste total con DeepSeek como implementador" vs. "con Claude/Codex"): se etiqueta explícitamente como tal — no hay benchmark verificado en esta sesión comparando calidad de código agentic de DeepSeek vs. Claude/Codex en SWE-bench u otro benchmark (los intentos de consulta a swebench.com y artificialanalysis.ai fallaron por ser páginas renderizadas en cliente que el fetcher no pudo leer; **sin verificar**).
- Cognition (3.5, patrón B) argumenta que compartir el *trace* completo de contexto entre el planificador y el ejecutor es lo que evita errores de reconciliación — un setup de dos vendors distintos (Claude planifica, DeepSeek ejecuta) por definición no puede compartir "agent traces" nativos entre sí (solo lo que se le pase explícitamente por texto en el issue), lo que es estructuralmente más parecido al escenario multi-agente que Cognition señala como frágil, aunque aquí no hay paralelismo sino una posta única secuencial (planificador → ejecutor), que mitiga bastante el riesgo que describe Cognition (que es específicamente sobre *paralelismo* de sub-agentes, no sobre secuencias). **Inferencia matizada**: el riesgo de Cognition aplica con fuerza a *paralelismo* multi-agente, no de forma directa a una posta secuencial planificador→ejecutor de un solo agente cada vez; no se encontró evidencia que compare directamente el caso secuencial de dos vendors.

**Balance**: no hay evidencia que diga explícitamente "no uses un modelo barato de otro vendor" ni evidencia que diga "usar dos vendors no tiene coste oculto". La single fuente más fuerte y consistente (dotnet/runtime) sugiere que el factor dominante del éxito es la calidad del issue, no la marca del modelo — lo cual **apoya débilmente** la hipótesis original siempre que se invierta en ingeniería de issues. Pero el hallazgo del cuello de botella de revisión (3.4) es un contrapeso real y verificado que la hipótesis original no menciona: cualquier ganancia de coste en la implementación puede consumirse en revisión si el modelo barato produce PRs peor especificadas o con más iteraciones. Confianza global de este balance: **media** — se apoya en hallazgos verificados pero la conclusión final (vale la pena o no) es una síntesis/inferencia propia, no una cita directa de una fuente que responda exactamente esta pregunta.

## 5. Dónde la hipótesis del usuario no se sostiene

Resumen explícito, releyendo 3.5 y 3.6 con la pregunta "¿la evidencia confirma issue→PR con Claude planificando y DeepSeek implementando, tal cual se planteó?":

1. **"Issue→PR" no es el único patrón validado — es uno de tres, y el mejor documentado en producción (patrón A, 3.5) es precisamente el que exige más disciplina de la que el enunciado da por hecha.** La evidencia de dotnet/runtime que sostiene el 67.9% de merge rate depende por completo de una inversión seria en documentación de repo (`.github/copilot-instructions.md`) e issues acotados a 1-50 líneas — no de "escribir un issue y lanzarlo". Si el sistema propuesto no incluye ese trabajo de preparación equivalente, la hipótesis de partida no tiene la base empírica que parece dar por hecha.
2. **La empresa que más agentes autónomos de codificación ha operado en producción (Cognition/Devin) recomienda explícitamente lo contrario a fragmentar el trabajo en piezas separadas ejecutadas por agentes distintos sin compartir el trace completo.** Esto no invalida issue→PR en sí (que es secuencial, no paralelo, y por tanto fuera del foco exacto de su crítica — ver 3.6), pero sí contradice la idea implícita de que "trocear en issues discretos y repartir a un ejecutor externo" es sin más la mejor forma de escalar: para tareas de tamaño medio, la postura con más peso de evidencia operativa real es *una sesión, un agente, contexto completo*, no *un issue, un ticket, un agente sin memoria del resto*.
3. **Ningún estudio ni documento oficial mide el escenario exacto que propone la hipótesis** (Claude como planificador vía Claude Code, modelo distinto como ejecutor vía issue formal, en un pipeline de dos vendors). Toda la evidencia de 3.6 es indirecta: se combina (a) que la preparación del issue importa más que el modelo, con (b) que el cuello de botella es la revisión, con (c) que hay varianza real de merge rate por agente. La conclusión "usar DeepSeek como ejecutor probablemente funciona si se invierte en issues buenos, pero puede trasladar coste a la revisión" es una **síntesis razonada, no un hallazgo verificado** — se marca así en 3.6 y se repite aquí para que quede explícito.
4. **La varianza de merge rate por agente (Codex 82.59% vs. Copilot 43.04%, mismo dataset — [arxiv.org/abs/2601.15195](https://arxiv.org/abs/2601.15195)) contradice la lectura optimista de "la marca del modelo importa poco".** Si el modelo/agente concreto puede producir una diferencia de casi 40 puntos porcentuales en tasa de merge en igualdad de condiciones de mercado, no es descartable que cambiar de Claude/Codex a DeepSeek como ejecutor tenga un efecto de magnitud similar — no hay datos que lo confirmen ni lo descarten para DeepSeek específicamente (benchmark de calidad agentic DeepSeek vs. Claude/Codex: **sin verificar**, intentos de consulta a swebench.com y artificialanalysis.ai fallidos por limitación de la herramienta de fetch en páginas renderizadas en cliente).
5. **Conclusión honesta**: la hipótesis del usuario **no está refutada**, pero tampoco está confirmada por evidencia directa. Lo que sí está confirmado es que (a) el patrón issue→PR funciona cuando se ejecuta con la disciplina que exige (documentación de repo, issues pequeños con criterios de aceptación), (b) la alternativa de sesión única sin pasar por un issue formal tiene defensores serios y evidencia operativa propia, y (c) el ahorro de usar un modelo barato como ejecutor puede compensarse — o no — en el cuello de botella de revisión, sin que exista todavía el estudio que zanje esa cuestión específica. Recomendación práctica (inferencia propia, no cita): probar el patrón A con DeepSeek vía OpenHands resolver en un subconjunto pequeño de issues reales, midiendo tasa de merge y comentarios de revisión por PR (las mismas dos métricas que usa el informe de dotnet/runtime), antes de comprometerse al pipeline completo de dos vendors.

- **Firma criptográfica de commits por agente** (GPG/Sigstore atribuyendo criptográficamente "este commit lo firmó el agente X, no un humano suplantándolo"): no se encontró evidencia de que ningún vendor lo haga hoy como estándar — el committer técnico en los dos casos verificados es una cuenta de servicio del propio vendor (`GitHub <noreply@github.com>`, `Claude <noreply@anthropic.com>`), no una firma verificable independientemente por terceros. **Sin verificar / posible hueco real**: ni Copilot coding agent ni claude-code-action firman criptográficamente el commit de forma que un tercero pueda verificar criptográficamente "esto lo generó el modelo X en la versión Y" sin confiar en el propio GitHub/Anthropic como intermediario.
- **Git notes** como mecanismo de trazabilidad de agentes: no se encontró evidencia de adopción real por ningún vendor de los estudiados; se buscó explícitamente y no apareció en ninguna de las fuentes consultadas. Tratar como no adoptado de facto, no como "no existe la posibilidad técnica".
- **Labels de PR estandarizados para origen-agente** (más allá de que el propio autor ya sea un bot visible): no se verificó una convención cross-vendor de labels (`agent:copilot`, `agent:claude`, etc.); lo único confirmado y suficiente en la práctica es la propia identidad de autor bot, que ya hace ese trabajo sin necesidad de un label adicional.
