Marcos (SSDF, ASVS, SLSA, Scorecard), toolchain por etapa con licencias e incidentes, calidad real de tests escritos por IA y no repudio.

Informe de un frente. La síntesis, con las decisiones pendientes, está en [[desarrollo-agentes-investigacion]].

Para un pipeline donde Claude planifica (casos de uso → issues) y agentes DeepSeek implementan código + tests vía PRs con CI/CD, con regla dura "sin código sin test" y umbrales de cobertura/complejidad por definir: ¿qué framework normativo (NIST SSDF/SSDF-AI, OWASP SAMM, ASVS, SLSA, OpenSSF Scorecard, CISA Secure-by-Design, EU CRA) y qué toolchain OSS por etapa (pre-commit, secretos, SAST, SCA, SBOM, IaC/contenedores, DAST, firma/provenance, policy-as-code) usan realmente equipos pequeños/medianos hoy (sept. 2026), con qué licencias/cambios recientes, y qué mecanismos (cobertura, patch-coverage, mutation testing, complejidad, tipado estricto, property-based testing) detectan de verdad tests débiles escritos por IA. Se excluye del alcance (ya investigado aparte): sandboxing del ejecutor de agentes, OWASP LLM Top 10, slopsquatting.

# 2. Descartado y por qué

- **Herramientas SAST/SCA comerciales cerradas (Snyk, Checkmarx One, Veracode, Semgrep Pro/AppSec Platform)**: fuera de alcance porque el encargo pide "opción OSS de facto + alternativas" con licencia; se mencionan solo como referencia de mercado, no como baseline recomendado para equipo pequeño autoalojado.
- **cosmic-ray (mutation testing Python)**: descartado frente a mutmut como opción principal — 658★ vs 1451★, cadencia de commits menor, comunidad más pequeña ([sixty-north/cosmic-ray](https://github.com/sixty-north/cosmic-ray), gh api, sept. 2026). Se mantiene como alternativa, no como recomendación.
- **radon como único medidor de complejidad Python**: el repo en GitHub no recibe push desde 2024-10-20 (gh api, sept. 2026) aunque PyPI sigue en 6.0.1; se prioriza lizard (multi-lenguaje, push 2026-09-16) para un pipeline con Python+lo-que-genere-DeepSeek, y radon se mantiene como complemento clásico para métricas Halstead/MI. — [rubik/radon](https://github.com/rubik/radon), [terryyin/lizard](https://github.com/terryyin/lizard)
- **DAST (OWASP ZAP) como gate bloqueante desde el día 1**: descartado como obligatorio inicial — solo aplica si el pipeline expone servicios HTTP; para un generador de código genérico sin superficie web garantizada es prematuro. Se deja como etapa opcional condicionada a que exista un endpoint desplegado.
- **CISA Secure-by-Design y EU CRA como controles técnicos de pipeline**: son marcos de responsabilidad de producto/fabricante y reporting regulatorio, no checklists de herramienta; se tratan en sección 3 solo como contexto normativo, no como fuente de controles de CI.
- **OWASP SAMM como gate automatizable**: SAMM es un modelo de madurez organizativo (autoevaluación), no una herramienta de CI; se usa para posicionar el programa, no para bloquear un PR. Se descarta como "tool" de pipeline y se mantiene como marco de gobernanza.
- **Prek (reimplementación en Rust de pre-commit)**: mencionado por ser tendencia 2025-2026 (adoptado por CPython, Airflow, FastAPI, Ruff), pero se descarta como recomendación por defecto por falta de metadatos de adopción verificados vía `gh api` en esta sesión (no se consultó su repo) — queda anotado como "por verificar", no como baseline.

# 2.5 Dónde la hipótesis del usuario no se sostiene

El encargo original describe el pipeline (Claude planifica, DeepSeek implementa vía PR, CI/CD con "sin código sin test") como si fuera ya una decisión de diseño. Desde el punto de vista DevSecOps que pide este frente, hay tres puntos donde esa hipótesis tiene un problema estructural, no cosmético:

1. **"Tests pasan" no es prueba de nada si el mismo agente (o familia de agentes) escribe código y tests.** Esto no es una objeción teórica: la sección 3.3 documenta con evidencia empírica que la cobertura alta en tests generados por IA convive con tasas de supervivencia de mutantes 15-25% más altas que en tests humanos — es decir, el agente puede (sin intención maliciosa, solo por optimizar la métrica visible) escribir un test que ejecuta la línea pero no verifica el comportamiento — [arxiv.org/pdf/2603.13724](https://arxiv.org/pdf/2603.13724). La regla "sin código sin test" tal como está planteada en el encargo no cierra esta brecha: exige *presencia* de test, no *independencia* del test respecto al código que verifica. Recomendación derivada: el gate de aceptación no puede ser solo "hay test y pasa" — necesita mutation testing sobre el diff (mide si el test *reacciona* a un cambio de comportamiento) y, si el presupuesto lo permite, que el mismo Claude que planificó el caso de uso (o un segundo modelo) revise el diff de test contra el issue original antes de mergear, no solo el diff de código. Esto es inferencia de diseño propia, apoyada en la evidencia de 3.3 — no una afirmación de una fuente que hable literalmente de este pipeline.
2. **Repartir planificación y ejecución entre dos proveedores de modelo distintos (Anthropic/Claude, DeepSeek) añade una frontera de confianza que el diseño actual no parece gestionar explícitamente.** Dos consecuencias concretas, no especulativas: (a) cada proveedor tiene su propia superficie de prompt-injection/exfiltración — un issue redactado por Claude a partir de una fuente externa (ticket de usuario, comentario de PR) podría ser el vector con el que un tercero influya en lo que DeepSeek termina implementando; esto es terreno de OWASP LLM Top 10, que el encargo ya excluye de este frente explícitamente, pero la implicación DevSecOps (validar/saneamiento del contenido del issue antes de pasarlo al agente implementador, tratar el issue como input no confiable) sí es un control de pipeline y debería estar en el backlog de F4 aunque el análisis profundo esté en otro frente. (b) Custodia del código fuente: si DeepSeek se consume como API alojada por el proveedor (no como pesos auto-hospedados), cada diff de código propietario sale de la infraestructura de la organización hacia un tercero antes de existir como commit — esto es un hecho de arquitectura, no de calidad de modelo, y tiene implicación directa en CRA/SSDF (control de dónde vive el código fuente antes de la build) y en cualquier cláusula de confidencialidad/IP. **Esto es inferencia general de arquitectura, no verificada contra los términos de servicio actuales de DeepSeek en esta sesión** (no se consultó; el presupuesto de búsqueda ya estaba agotado) — se señala como pregunta abierta en sección 6, no como hecho corroborado. Mitigación estándar si aplica: usar pesos abiertos de DeepSeek auto-hospedados en infraestructura propia en vez de la API del proveedor, lo cual además es coherente con NIST SP 800-218A (gobernar el modelo como parte de la cadena de suministro propia) — [csrc.nist.gov/pubs/sp/800/218/a/final](https://csrc.nist.gov/pubs/sp/800/218/a/final).
3. **El handoff planificador→implementador sin gate humano síncrono para cambios sensibles (auth, cripto, IaC con credenciales de producción, cualquier cosa con superficie ASVS L2/L3) no está contemplado como excepción en la hipótesis original.** El resto de este documento (3.4) asume que hay categorías de cambio donde un mutation-testing gate y un SAST limpio no son suficientes y hace falta revisión humana bloqueante — esto es coherente con el propio ASVS (los requisitos L2/L3 son, por diseño, más caros de verificar automáticamente) y con OSPS Baseline nivel 2-3 ("mandatory code review approvals" — [baseline.openssf.org](https://baseline.openssf.org/versions/2026-02-19.html)). Si el pipeline trata todo PR de DeepSeek igual (test verde = merge automático), esto es un punto donde la hipótesis inicial choca con la práctica documentada, no un exceso opcional.

## 3.3 Calidad de test para código generado por IA — qué detecta de verdad tests débiles

| Mecanismo | Herramienta de facto | Qué detecta / qué NO detecta cobertura sola | Evidencia |
|---|---|---|---|
| Cobertura de línea/rama | coverage.py + pytest-cov (Python); c8/istanbul (Node) | Mide qué se ejecuta, no si la aserción es correcta. Caso documentado: 12 tests generados con ~85% cobertura de código pero solo 57.3% de mutantes muertos — la cobertura alta "mintió" sobre la calidad real | [medium.com/@outsightai](https://medium.com/@outsightai/the-truth-about-ai-generated-unit-tests-why-coverage-lies-and-mutations-dont-fcd5b5f6a267) (practitioner report, confianza media — caso único, no estudio con muestra) |
| Patch/diff coverage | diff-cover (Python, `Bachmann1234/diff_cover`, 844★, activo); Codecov `patch` status (SaaS) | Gate específico para "¿las líneas que tocó este PR están testeadas?" — el control correcto para un pipeline donde cada PR es generado por un agente distinto y la cobertura global puede diluir un archivo mal testeado. Codecov: `target: auto` compara contra rama base, `threshold` configurable, gate en CI antes de merge | [docs.codecov.com/docs/commit-status](https://docs.codecov.com/docs/commit-status) (oficial, alta confianza) |
| Mutation testing | Python: mutmut (1451★) > cosmic-ray (658★, menor actividad); JS/TS: Stryker (`stryker-js`, 3145★, activo) | Esto es lo que de verdad separa "test que ejecuta la línea" de "test que falla si el comportamiento cambia". Evidencia cuantitativa: en tests generados por IA, la tasa de supervivencia de mutantes es 15-25% más alta que en tests humanos a igualdad de cobertura de línea; estudio MutGen: prompt LLM básico → 53% mutation score en HumanEval-Java, con feedback de mutantes supervivientes → 89.5% | [arxiv.org/pdf/2603.13724](https://arxiv.org/pdf/2603.13724) (paper, empírico), [engineering.fb.com](https://engineering.fb.com/2025/09/30/security/llms-are-the-key-to-mutation-testing-and-better-compliance/) (Meta engineering, practitioner+vendor-interno), [ceur-ws.org/Vol-4057/paper4.pdf](https://ceur-ws.org/Vol-4057/paper4.pdf) (paper académico) — **3 fuentes independientes, mezcla de papers y reporte de ingeniería de Meta, confianza alta en la conclusión general ("coverage alta ≠ tests fuertes para código IA"), confianza media en las cifras exactas (provienen de benchmarks específicos, no de una medición sobre este pipeline)** |
| Complejidad ciclomática | Python: radon (2030★, repo estancado desde oct-2024) + lizard (2521★, activo, multi-lenguaje); JS/TS: ESLint `complexity` rule | Gate de "este PR generado introduce una función con complejidad >X" — proxy de mantenibilidad, no de corrección; útil como señal de que el agente generó una solución enrevesada en vez de simple | [radon.readthedocs.io](https://radon.readthedocs.io/en/latest/), [terryyin/lizard](https://github.com/terryyin/lizard) — documentación oficial de herramienta, sin estudio de eficacia específico para código IA encontrado (inferencia: la complejidad ciclomática es proxy general de mantenibilidad, no verificado específicamente contra código generado por LLM en esta sesión) |
| Tipado estático estricto | mypy (20648★) o pyright (15656★) en modo strict; `tsc --strict` | Atrapa una clase entera de errores (None, tipos incompatibles) antes de ejecutar test alguno — barato y determinista, buen primer gate para código IA que a menudo "funciona" pero rompe contratos de tipo | [pydevtools.com/handbook/explanation/how-do-mypy-pyright-and-ty-compare](https://pydevtools.com/handbook/explanation/how-do-mypy-pyright-and-ty-compare/) (guía técnica, practitioner) — patrón recomendado: pyright en editor + mypy o pyright strict como gate único de CI (no correr dos checkers distintos como gate, genera supresiones cruzadas) |
| Property-based testing | Hypothesis (Python, 9009★); fast-check (JS/TS, 5155★) | Genera cientos de inputs aleatorios contra invariantes declaradas — encuentra los edge cases que un LLM sistemáticamente no genera porque optimiza para el patrón común de su entrenamiento | [arxiv.org/pdf/2510.25297](https://arxiv.org/pdf/2510.25297) (paper específico sobre tests property-based generados por LLM), [arxiv.org/pdf/2605.15229](https://arxiv.org/pdf/2605.15229) (PBT-Bench, benchmark de agentes IA en PBT) — 2 papers independientes, confianza media-alta en que PBT complementa bien la ceguera a edge cases de LLMs, aunque ambos son trabajos recientes (2025-2026) sin replicación amplia todavía |

**Conclusión de la sección**: la cobertura de línea es necesaria pero no suficiente y por sí sola es fácil de "engañar" por un agente que genera tests triviales para cumplir el número — esto está corroborado por múltiples fuentes independientes (paper arxiv, ingeniería de Meta, casos de práctica). El gate real de calidad para código generado por IA es **patch-coverage (bloquea PR sin tests en las líneas tocadas) + mutation testing sobre el diff (no sobre todo el repo, por coste)** — el patrón "incremental mode" de Stryker y el modo "solo tests relevantes por mutante" hacen esto viable en CI por PR (1-5 min reportado) — [oneuptime.com/blog/post/2026-01-25-mutation-testing-with-stryker](https://oneuptime.com/blog/post/2026-01-25-mutation-testing-with-stryker/view) (practitioner, confianza media, cifra de tiempo no verificada independientemente).

## 3.4 Pipeline base mínimo pero completo (equipo pequeño autoalojado)

Basado en OWASP DevSecOps Guideline (7 etapas: Design/Develop/Build/Test/Release/Deploy/Operate, con lista de herramientas por etapa) — [OWASP/DevSecOpsGuideline](https://github.com/OWASP/DevSecOpsGuideline), [devguide.owasp.org/en/09-operations/01-devsecops](https://devguide.owasp.org/en/09-operations/01-devsecops/) — y OSPS Baseline nivel 1-2 (proyecto pequeño con pocos mantenedores) — [baseline.openssf.org](https://baseline.openssf.org/versions/2026-02-19.html):

| Etapa | Estándar (hacer siempre) | Overkill para equipo pequeño en día 1 |
|---|---|---|
| Pre-commit | pre-commit framework + gitleaks + linters de lenguaje | Firma GPG de cada commit local |
| Push/PR | GitHub push protection (gratis) + branch protection + revisión obligatoria | CODEOWNERS granular por microservicio si hay 1 repo monolito |
| SAST | Semgrep CE u Opengrep con reglas por defecto + Bandit si hay Python | Reglas Pro/comerciales, SAST múltiple redundante (Semgrep+CodeQL+otro) desde el día 1 |
| SCA | Dependabot o Renovate + OSV-Scanner | Escaneo de licencias exhaustivo tipo FOSSA desde el inicio |
| Secretos | gitleaks en CI + push protection | trufflehog con verificación en vivo en cada PR (mejor como job nocturno/histórico) |
| SBOM | Syft generando CycloneDX en cada release | Firmar y publicar SBOM públicamente si el CRA aún no aplica (deadline real: sept-2026/dic-2027) |
| Contenedor/IaC | Trivy (fs+config+image en un solo comando) | Checkov + KICS + Trivy los tres a la vez (redundante; elegir uno, KICS si se usa mucho OPA/Rego) |
| Tests + gate IA | coverage.py/c8 + **diff-cover o Codecov patch gate obligatorio** + mypy/pyright strict | Mutation testing sobre el repo completo en cada PR (correr solo sobre el diff / nightly full run) |
| Firma/provenance | GitHub Artifact Attestations (nativo, gratis, basado en Sigstore) para builds/releases | SLSA L3 completo (build aislado con secretos de firma fuera del step) — normalmente innecesario hasta que haya consumidores externos del artefacto |
| DAST | Solo si hay endpoint desplegado: ZAP baseline scan | ZAP full active scan en cada PR (lento, mejor nightly/staging) |
| Policy gate final | Conftest/OPA sobre manifiestos antes de deploy | Motor de políticas custom propio en vez de Rego ya maduro |

Esto coincide con la filosofía de "shift-left progresivo" del OWASP DevSecOps Guideline (people/process/governance) y con los 3 niveles de OSPS Baseline (empezar en nivel 1, subir a nivel 2 cuando haya más de un mantenedor activo). ## 3.5 Auditabilidad y no repudio — atribuir cada cambio a agente/modelo/humano

Control DevSecOps añadido a petición explícita: en un pipeline donde varios agentes (y potencialmente varias versiones de modelo) generan commits, la capacidad forense de responder "¿qué identidad, con qué versión de modelo, a partir de qué prompt/issue, produjo esta línea?" no es opcional — es lo que exige SSDF PO.3/PS.1 (gestionar la cadena de suministro del propio proceso de build) y lo que empieza a formalizar SLSA con su **Source Track**, añadido en la revisión v1.2 (no existía como tal en v1.1) — verificado directamente en [slsa.dev/spec/v1.2/](https://slsa.dev/spec/v1.2/) (oficial, alta confianza).

**Qué exige el SLSA Source Track (verificado vía WebFetch a [slsa.dev/spec/v1.2/source-requirements](https://slsa.dev/spec/v1.2/source-requirements), oficial):**
- El sistema de control de versiones (SCS) "MUST record all changes to Named References, including when they occurred, who made them, and the new Source Revision ID" — historia no reescribible, solo avance a revisiones descendientes.
- Las actividades sensibles "SHOULD be attributed to authenticated identities" — el mecanismo de autenticación concreto (SSO, claves criptográficas) queda abierto, pero la exigencia de identidad autenticada por cambio es explícita.
- Desde el **nivel 2** del Source Track, el SCS debe generar **atestaciones de procedencia de revisión contemporáneas** ("revision provenance") — evidencia resistente a manipulación de cuándo, quién y bajo qué controles técnicos se hizo cada cambio.
- La autenticación "fuerte" (resistente a phishing, protección contra robo de token) queda explícitamente en "Future Considerations" — es decir, el propio SLSA reconoce que hoy no exige MFA fuerte por defecto; para un pipeline con agentes autónomos con credenciales de escritura, esto es una brecha a cerrar por diseño propio, no algo que SLSA resuelva solo.

**Patrón de referencia ya implementado en producción — GitHub Copilot coding agent** (verificado vía WebFetch a la doc oficial de tracking de sesiones, [docs.github.com/copilot/.../track-copilot-sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions), oficial, alta confianza). Mecanismo de 4 capas, directamente trasladable a un agente DeepSeek self-hosted:
1. **Identidad de bot separada, no la del humano que disparó la tarea**: los commits los autoría "Copilot", con la persona que inició la tarea como *co-author* en el trailer — cadena de responsabilidad clara sin borrar quién lo pidió.
2. **Firma criptográfica de cada commit del agente**, verificable ("Verified" en GitHub) — usando GitHub confirma que "organizations and GitHub Apps that require commit signing can use bots to sign commits" con clave gestionada por la GitHub App, no por una persona — [docs.github.com/en/authentication/.../about-commit-signature-verification](https://docs.github.com/en/authentication/managing-commit-signature-verification/about-commit-signature-verification) (oficial).
3. **Enlace en el mensaje de commit al log de sesión** — el razonamiento interno y las herramientas que usó el agente quedan trazables para auditoría o revisión de código, sin depender solo de leer el diff.
4. **Audit log de organización** captura actor, acción, repo, fecha/hora y país, con capacidad de filtrar por actor específico (p.ej. `actor:Copilot`) — retención de 180 días por defecto — [docs.github.com/.../reviewing-the-audit-log-for-your-organization](https://docs.github.com/en/organizations/keeping-your-organization-secure/managing-security-settings-for-your-organization/reviewing-the-audit-log-for-your-organization) (oficial).

**Traducción a un pipeline con DeepSeek (inferencia propia, no una guía oficial "para DeepSeek" — no existe tal cosa)**: replicar el patrón de Copilot requiere, como mínimo — (a) una identidad de máquina distinta por rol de agente (p.ej. `deepseek-implementer-bot`, no la cuenta personal de nadie ni una identidad compartida entre todos los agentes), con clave de firma de commit gestionada por el propio runner de CI, nunca por el modelo; (b) trailer `Co-authored-by`/`Requested-by` apuntando al issue o al usuario que disparó el caso de uso planificado por Claude, para no perder la cadena planificador→issue→implementador; (c) publicar el log de razonamiento/prompt del agente (o un hash/referencia verificable si el contenido es sensible) enlazado desde el commit, análogo al session log de Copilot; (d) generar una atestación de procedencia (GitHub Artifact Attestations, ya cubierto en 3.2, basado en Sigstore) en el momento del build, no solo confiar en el commit firmado — esto cierra la distancia entre "quién escribió el código" (Source Track) y "cómo se construyó el artefacto" (Build Track), que es exactamente la separación que introduce SLSA v1.2 entre sus dos tracks; (e) activar y exportar el audit log del forge (GitHub/GitLab) a almacenamiento propio antes de que expiren los 180 días por defecto, si hay requisito de retención más largo (relevante de cara a obligaciones de reporte de incidentes del EU CRA, sección 3.1).

Confianza global de esta subsección: **alta** en los mecanismos disponibles hoy (todos verificados contra documentación oficial de SLSA y GitHub); **media** en la traducción concreta a "cómo hacerlo con DeepSeek" porque es diseño propio razonado sobre un patrón existente, no una receta publicada para este caso.

7. **No se verificaron los términos de servicio/custodia de datos de DeepSeek** (API alojada por el proveedor vs despliegue de pesos abiertos auto-hospedados) en esta sesión — es el hueco de evidencia más relevante para la sección 2.5, punto 2 (custodia de código fuente propietario al repartir el pipeline entre dos proveedores de modelo). Antes de fijar la arquitectura del pipeline, verificar directamente: (a) política de retención/uso de datos de la API de DeepSeek para inputs de código, (b) si hay opción de despliegue self-hosted de pesos abiertos (DeepSeek publica algunos modelos con pesos abiertos) que evite la salida de código fuera de infraestructura propia, (c) cualquier implicación de control de exportación aplicable según jurisdicción del equipo.
8. El Source Track de SLSA v1.2 es señalado aquí porque resolvió exactamente el vacío de no-repudio que preguntó el usuario, pero es una adición reciente de la spec — no se verificó cuántos forges (GitHub, GitLab, Gitea) certifican ya niveles concretos del Source Track en producción; queda pendiente si se quiere exigir "SLSA Source L2" como requisito formal en vez de usarlo solo como marco de referencia.
