Subtarea de evaluación profunda encargada por el orquestador, sesión única, sin subagentes, sin navegador. Herramientas: `gh` (CLI oficial de GitHub, incluida lectura de código fuente e issues), `WebFetch`/`curl` contra documentación y APIs públicas, HN Algolia. Fecha: 2026-09-25. Sigue [[circuito-tareas-definicion]] — criterios C1–C13 (§5), requisitos del estado del trabajo R1–R13 (§5 bis), definición de «contrastado» (§7), reglas de evidencia (§8).

**MCP** (*Model Context Protocol*): protocolo estándar que expone herramientas a un agente de IA, independiente del modelo. **SDD** (*Spec-Driven Development*, desarrollo dirigido por especificación): escribir una especificación estructurada antes que el código, y usarla como fuente de verdad para el agente. **Lease**: reserva con caducidad automática. **Claim**: reserva de una pieza de trabajo por un agente. **CAS** (*Compare-And-Swap*): escritura condicional que solo tiene efecto si el valor no ha cambiado desde que se leyó — mecanismo típico para evitar que dos escritores concurrentes se pisen.

## 1. Método

Dos componentes evaluados por separado, con el mismo rigor para todos los candidatos independientemente de quién los mencionó primero (el usuario, la fase A, o el barrido B/B2):

1. **Spec/descomposición**: cómo un diseño se convierte en piezas de trabajo que un implementador puede coger. Candidatos: `github/spec-kit`, `Fission-AI/OpenSpec`, `bmad-code-org/BMAD-METHOD`, Kiro specs (kiro.dev), y la práctica de «plan como contrato verificable» de fase A (`until-dev/plugins` como ejemplo).
2. **Estado del trabajo**: dónde vive el trabajo pendiente cuando un agente lo coge. Candidatos: `gastownhall/beads`, `MrLesk/Backlog.md`, GitHub Issues + sub-issues + Projects v2 (+ labels/assignees como *claim*), *shared task list* de Claude Code agent teams (`~/.claude/tasks`), ficheros `tasks.md` de los frameworks de spec, `eyaltoledano/claude-task-master`, `wedow/ticket`. Se añade `openai/symphony` como referencia cruzada con A2 (sin re-verificación primaria propia en esta sesión, se marca así).

**Fuentes primarias usadas por candidato**: READMEs completos descargados vía `gh api repos/<owner>/<repo>/readme` (no resúmenes), código fuente descargado y grepeado cuando el README no bastaba para R3/R4 (caso `wedow/ticket`: se descargó y leyó el script bash completo, 1.383 líneas), páginas de documentación oficial vía `curl`/`WebFetch` con extracción de texto plano, `gh search issues`/`gh issue list` sobre cada repo de estado del trabajo para evidencia en contra, HN Algolia API para cobertura independiente.

**Lo que NO se hizo por presupuesto de tiempo**: no se instaló ninguna herramienta (prohibido por el encargo); no se probó `bd claim`/`backlog task edit`/etc. en vivo, todo el análisis de R3/R4 es lectura de código y documentación, no observación empírica; no se re-verificó `openai/symphony` en profundidad (se remite a A2 Fuente 6); no se encontró la página exacta de «modelos soportados» de Kiro (dos URLs probadas devolvieron 404), así que la afirmación de exclusividad a modelos Claude en Kiro queda atribuida a una fuente secundaria (OpenSpec, un competidor) y marcada «sin verificar en fuente primaria de Kiro».

### 2.2 Notas por candidato

**spec-kit** es, con diferencia, el más adoptado (138.825★, frente a 70.283 de OpenSpec) y el único con historial de vídeo/documentación de proyecto public (`history.html`). Fuente independiente y no comercial — Birgitta Böckeler (Distinguished Engineer, Thoughtworks), [«Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl»](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), martinfowler.com, 15-oct-2025, 128 puntos en HN ([hilo](https://news.ycombinator.com/item?id=45610996)) — describe el flujo real observado: *«Workflow: Constitution → (Specify → Plan → Tasks)»*, confirma que **spec-kit crea una rama por spec**, lo que la autora interpreta como evidencia de que spec-kit es «spec-first» (la especificación se usa para construir, no necesariamente se mantiene viva después) y no plenamente «spec-anchored», pese a la retórica de GitHub sobre specs como «living, executable artifacts». Cita textual de GitHub recogida por la misma autora: *«Crucially, your role isn't just to steer. It's to verify. At each phase, you reflect and refine.»* Nota: el artículo es de octubre de 2025, un año antes de esta investigación; el propio spec-kit ha cambiado desde entonces (extensiones de *bug fixing* e *idea assessment* añadidas, ver README actual), así que el detalle puede estar desactualizado aunque el marco analítico (spec-first / spec-anchored / spec-as-source) sigue siendo útil.

**OpenSpec** es el único de los tres frameworks de SDD que declara explícitamente **multi-arnés con 30+ herramientas** y documenta la sintaxis exacta de invocación por herramienta (algo que ni spec-kit ni BMAD hacen con el mismo detalle en su README). Su comparación directa contra spec-kit («Thorough but heavyweight. Rigid phase gates, lots of Markdown, Python setup») y contra Kiro («Powerful but you're locked into their IDE and limited to Claude models») es una **afirmación de vendor sobre productos ajenos**, no contrastada de forma independiente aquí — se cita como tal, no como hecho. La función `Stores` (beta, lanzada en 2026) es la respuesta directa de OpenSpec al problema de traspaso cross-repo que fase A2 documentó como sin resolver de forma satisfactoria por ningún candidato.

**BMAD-METHOD** es la única de las tres con un modelo explícito de **roles ágiles humanos-como-agentes** (product, arquitectura, UX, desarrollo, testing) discutiendo entre sí antes de llegar a tareas — más cercano al patrón MetaGPT (ya en B) que a spec-kit/OpenSpec. Su tercer módulo, **BMad Loop** («Builds, verifies, and retros a whole epic unattended»), es un candidato adicional no explorado en profundidad para el patrón de bucle de revisión (C6), pendiente si hace falta profundizar.

**Kiro** es el único de los cuatro con una función de producción de **paralelismo automático por dependencias** (waves) documentada oficialmente — encaja directo con C5 (topología) y con el patrón SPOQ citado en B2. Su debilidad frente al resto: no es un toolkit abierto sino un producto cerrado (IDE/CLI/web propios de AWS), y la afirmación de exclusividad a Claude viene de un competidor, no de AWS.

**`until-dev/plugins`** confirma el hallazgo central de fase A («el traspaso funciona cuando es un contrato verificable, falla cuando es prosa de intención»), pero como implementación es marginal (31★, un solo caso de uso documentado). Su valor aquí es conceptual, no como candidato operable: apunta a que **el criterio de aceptación como contrato comprobado automáticamente contra el resultado**, no solo declarado en el plan, es el elemento que ninguno de los cuatro frameworks de arriba automatiza de forma nativa (todos generan el checklist; ninguno de los README leídos describe una verificación automática post-hoc del código final contra los criterios de aceptación, más allá de que el propio agente marque la casilla).

**Conclusión de C1 (parcial) sobre spec/descomposición**: los cuatro frameworks convergen en un patrón de tres-a-cuatro artefactos Markdown versionados en git (`spec.md`/`proposal.md`/`requirements.md`, `plan.md`/`design.md`, `tasks.md`), generados por comandos slash o skills invocables desde cualquier arnés compatible. La granularidad de la tarea final es siempre una lista con criterios de aceptación (formato GIVEN/WHEN/THEN en Kiro, checklist marcado en OpenSpec/spec-kit), **no un objeto con campos estructurados ni estado persistente propio** — el `tasks.md` es un documento de planificación de una sola pasada, no un sistema de coordinación en curso. Esto tiene una consecuencia directa para la sección 3: **ninguno de los cuatro resuelve por sí solo R3/R4/R5** (claim atómico, recuperación de reservas, IDs sin colisión) — el `tasks.md` necesita entregarse a un sistema de estado del trabajo aparte para eso.

### 3.1 Notas con evidencia, por requisito crítico (R3, R4, R6, R13 — se pidió leer código, no solo README)

**R3 — Claim atómico**

- **`beads`** ✅, primario y confirmado en el propio comando: `bd update <id> --claim` → *«Atomically claim a task (sets assignee + in_progress)»* ([README](https://github.com/gastownhall/beads/blob/main/README.md)). El backend es [Dolt](https://github.com/dolthub/dolt), una base de datos SQL versionada; el modo por defecto es **de un solo escritor** («Embedded (default) — `bd init`. Dolt runs in-process, ... single writer»), lo que garantiza atomicidad por serialización, no por CAS explícito documentado.
- **Claude Code agent teams** ✅, cita literal ya verificada por B2 y re-confirmada aquí sobre el `.md` completo (485 líneas, descargado de nuevo en esta sesión): *«Task claiming uses file locking to prevent race conditions when multiple teammates try to claim the same task simultaneously»* ([agent-teams.md](https://code.claude.com/docs/en/agent-teams)).
- **GitHub Issues** ❌, confirmado por lectura directa de la documentación oficial de asignación: *«You can assign multiple people to each issue or pull request... Both issues and pull requests support up to 10 assignees»* ([docs.github.com](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/assigning-issues-and-pull-requests-to-other-github-users)). Asignar es **aditivo, no exclusivo**: no hay ninguna operación de la API que falle si el issue ya tiene asignado a otro agente — dos agentes pueden auto-asignarse el mismo issue sin conflicto detectado por la plataforma. Labels tienen el mismo problema (añadir una label no es exclusivo). **No existe reserva atómica nativa**; construirla requiere una capa externa (p. ej. un *lock* en un fichero, o comprobar-y-escribir vía Actions con reintento).
- **`Backlog.md`** ❌: el campo `assignee` se edita con `backlog task edit BACK-1 -a @sara`, un comando CLI que escribe el fichero Markdown de la tarea. El README no documenta ninguna comprobación de "ya asignado" ni bloqueo; el modelo es de edición de fichero de texto, análogo a Issues sin la ventaja de la API centralizada.
- **`wedow/ticket`** ❌, confirmado leyendo el script bash completo (1.383 líneas, descargado en esta sesión): `cmd_start()` llama a `cmd_status "$1" "in_progress"`, que llama a `update_yaml_field` → un `sed`/`mv` incondicional sobre el fichero. **Cero apariciones de `flock` en todo el script.** No hay comprobación de si el ticket ya está `in_progress`, ni bloqueo de fichero, ni CAS. Dos agentes ejecutando `tk start X` a la vez pueden ambos "ganar" sin error. Esto es coherente con el propio origen del proyecto (ver R4/evidencia en contra): se escribió explícitamente para huir del demonio de `beads`, y sacrificó la atomicidad a cambio de simplicidad.
- **`tasks.md` de los frameworks de spec** ❌: son ficheros Markdown de planificación, editados por el propio agente que los marca como completados; no tienen mecanismo de reserva en absoluto — la exclusión mutua, si existe, la aporta quien los entrega a otro sistema (p. ej. Beads, Issues).
- **`claude-task-master`** ❓: no se ha leído el código fuente de los comandos de asignación en esta sesión (repo grande, 5 meses sin commits — ver §4); el README documenta `task-master` como orientado a un único desarrollador+agente en un editor, no a coordinación multiagente concurrente, así que R3 es probablemente poco relevante para su caso de uso diseñado, pero no se afirma sin verificar.

**R4 — Recuperación de reservas abandonadas (lease/caducidad)**

- **`beads`** ⚠️: existe un mecanismo de *lease* con caducidad, pero con un defecto documentado por los propios mantenedores. Issue abierta: *«Make the claim lease TTL configurable (hardcoded 5m; claim.ttl is accepted but inert)»* ([#5681](https://github.com/gastownhall/beads/issues/5681)) — confirma que **hay** un TTL de 5 minutos hardcodeado (mecanismo de lease real, no inventado), pero el parámetro para cambiarlo (`claim.ttl`) se acepta sin efecto: un bug de configuración, no ausencia del mecanismo. Se cuenta como cumplimiento parcial: el mecanismo existe y es real, pero no es configurable como se documenta.
- **Claude Code agent teams** ❌: no hay lease. La documentación describe el fallo abierto explícitamente como una limitación conocida, no como algo resuelto: *«Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks. If a task appears stuck, check whether the work is actually done and update the task status manually or tell the lead to nudge the teammate»* ([agent-teams.md](https://code.claude.com/docs/en/agent-teams)). Recuperación manual, no automática.
- **GitHub Issues** ❌: sin mecanismo nativo. Un asignado que abandona el trabajo deja el issue asignado indefinidamente hasta que alguien lo quite a mano.
- **`Backlog.md`, `wedow/ticket`** ❌: mismo problema — el campo de estado/asignado no caduca solo, requiere intervención manual (`backlog task edit --assignee ""` o `tk reopen`).
- Este es exactamente el requisito que motiva R4 en `circuito-tareas-definicion.md` §5 bis, citando el fallo de Symphony en fase A2 (estado de orquestación en memoria, sin recuperación documentada tras caída del proceso — no re-verificado aquí, remite a A2).

**R6 — Sincronización entre máquinas y agentes**

- **`beads`** ⚠️, con un matiz importante que **corrige la caracterización de B/B2** («grafo de tareas... persistido en git»): la fuente de verdad real es la base de datos Dolt, no el JSONL ni git. Cita literal de la documentación propia: *«Beads issue data lives in Dolt. The local Dolt database is the source of truth for `bd list`, `bd show`, `bd ready`, and every write command... `.beads/issues.jsonl` is an export for viewers and interchange, not the source of truth»* ([docs/core-concepts/sync-concepts.md](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/sync-concepts.md)). La sincronización entre máquinas usa `bd dolt push`/`bd dolt pull` contra `refs/dolt/data` en el remoto git — **es una operación manual/por hook**, no automática ni en tiempo real; si dos agentes en dos máquinas no sincronizan, ven estados distintos hasta el siguiente push/pull. Se marca ⚠️ porque el mecanismo existe y es real, pero no resuelve "el estado difiere según dónde se mire" en tiempo real, solo tras sincronizar explícitamente.
- **GitHub Issues, `Backlog.md`, `wedow/ticket`, `tasks.md`**: ✅ por diseño — viven en el propio repo remoto (Issues vía API centralizada; los otros tres vía git), cualquier máquina con acceso al remoto ve el mismo estado tras `git pull`/consulta a la API.
- **Claude Code agent teams** ❌: confirmado explícitamente en la documentación oficial: *«The task list directory persists locally and is never uploaded, so resumed sessions keep their tasks»* ([agent-teams.md](https://code.claude.com/docs/en/agent-teams)) — el estado vive en `~/.claude/tasks/{team-name}/` **solo en la máquina donde corre la sesión**. No hay sincronización entre máquinas en absoluto; un equipo distribuido en varias VMs no puede compartir una lista de tareas de agent teams.

**R13 — Coste operativo asumible en la VM (4 núcleos, 7 GB RAM, sin motor de contenedores)**

- **`beads`** ❌, la evaluación más negativa de la matriz, con evidencia directa de issues abiertas (no cerradas, no negadas por los mantenedores):
  - Demonios huérfanos que consumen CPU/RAM de forma continua: *«Embedded dolt sql-server daemons are never reaped on inactive projects — 7 orphaned servers, several at ~38% CPU / ~2 GB RSS, ~67 W battery drain»* ([#4282](https://github.com/gastownhall/beads/issues/4282)).
  - Contención de bloqueos que bloquea toda la herramienta: *«`bd list --watch` holds embedded-Dolt lock for its lifetime, blocking all other bd commands»* ([#3415](https://github.com/gastownhall/beads/issues/3415)).
  - Corrupción de base de datos, múltiples issues abiertas simultáneamente: *«Dolt journal corruption and stale DB locks on batch timeout»* ([#4521](https://github.com/gastownhall/beads/issues/4521)); *«bd does not restart dolt sql-servers after an upgrade; old server + new client corrupted a journal»* ([#6064](https://github.com/gastownhall/beads/issues/6064)); *«Concurrent label updates on one issue silently lose or duplicate labels»* ([#5657](https://github.com/gastownhall/beads/issues/5657)).
  - El modo **servidor** (necesario para más de un escritor concurrente, es decir, para varios agentes escribiendo a la vez) requiere un proceso `dolt sql-server` externo permanente — un demonio de base de datos, exactamente el tipo de complejidad que R13 y la crítica de HN citada en `circuito-tareas-definicion.md` (§5 bis, [item 46487580](https://news.ycombinator.com/item?id=46487580)) señalan como no asumible.
  - **Verificación directa de esa crítica de HN** (encargo explícito del orquestador — "Show HN: I replaced Beads with a faster, simpler Markdown-based task tracker", 84 puntos): el autor de `wedow/ticket` explica en el propio hilo por qué lo escribió: *«I've been running long duration coding agents with Claude Code for about 6 months now... But Beads grew massively in a short time and every release made it slower and more frustrating to use. I started battling it several times a week as its background daemon took to syncing the wrong things at the wrong times. Over the holidays I finally ripped it out and wrote ticket as [a replacement]»* ([hilo completo](https://hn.algolia.com/api/v1/items/46487580)). Esto es **evidencia de primera mano de abandono documentado por su propio autor tras 6 meses de uso en producción**, no una opinión de paso — cumple el estándar de «contrastado» de §7 (fuente primaria con experiencia propia).
  - Conclusión sobre R13 para `beads`: en modo *embedded* por defecto (single-writer), el coste es más bajo pero limita la concurrencia real entre agentes a uno-escribe-a-la-vez; en modo *server* (el que de verdad soporta varios agentes escribiendo a la vez, que es el escenario que motiva este proyecto), se necesita un proceso de base de datos persistente — no encaja bien en 4 núcleos / 7 GB sin vigilancia activa, y hay evidencia documentada (no solo especulación) de fugas de recursos por demonios no purgados.
- **GitHub Issues+Projects v2**: ✅ — sin infraestructura propia que mantener, la carga la lleva GitHub; el coste es solo llamadas a la API REST/GraphQL desde el script del agente.
- **`Backlog.md`, `wedow/ticket`**: ✅ — ambos son CLI sin servidor ni base de datos: `Backlog.md` opera sobre ficheros Markdown con un binario TypeScript/Bun; `ticket` es *«a portable bash script requiring only coreutils»* con web server opcional que escucha solo en localhost. Coste mínimo, confirmado por diseño y por el propio origen de `ticket` (reacción directa al coste de `beads`).
- **Claude Code agent teams**: ✅ — no hay proceso adicional más allá de las sesiones de Claude Code ya en marcha; el coste real es tokens (C9), no infraestructura, aunque cada teammate es una sesión completa (más RAM/CPU en el propio proceso `claude` por cada uno, sin verificar cifras exactas).

## 5. Interfaces de los candidatos principales

Documentación exacta de cómo interactúan un agente (de cualquier modelo) y un script, con comandos y formatos literales encontrados en la fuente primaria.

### `beads`

- **CLI con salida JSON**: `bd ready --json`, `bd update bd-a1b2 --claim`, `bd show <id>`, `bd create "Title" -p 0`.
- **MCP**: paquete `beads-mcp` publicado en PyPI (badge en el README: `pypi.org/project/beads-mcp`) — no se ha leído la lista exacta de herramientas MCP expuestas en esta sesión, **sin verificar en detalle**.
- **Git**: no usa git como transporte del estado (§3.1, R6) — usa remotos Dolt (`refs/dolt/data`) que pueden vivir en el mismo repositorio git de origen; `bd init` detecta automáticamente `git remote get-url origin`.
- **Vínculo a rama/PR/commit**: el README no documenta un comando nativo tipo `bd link-pr`; el enlace con GitHub existe como integración opcional (`bd setup claude`, `bd setup codex` instalan hooks/`AGENTS.md`, no vínculo issue↔PR nativo documentado en el README) — **sin verificar en profundidad**, remite a `docs/integrations/` no leído en esta sesión.

### `Backlog.md`

- **CLI con salida JSON estable y versionada**: `backlog task list --json`, `backlog task view <id> --json`, `backlog task list --json --watch` (modo *streaming*: primera respuesta con la lista completa, luego reemplazos completos ante cada cambio) — cita literal: *«Read commands support stable, versioned JSON for scripts and integrations»* ([README](https://github.com/MrLesk/Backlog.md/blob/main/README.md)).
- **MCP**: servidor con nombre fijo `backlog`, arrancado con `backlog mcp start`; alta con un comando por arnés: `claude mcp add backlog --scope user -- backlog mcp start` (Claude Code), `codex mcp add backlog -- backlog mcp start` (Codex), `gemini mcp add backlog -s user backlog mcp start` (Gemini CLI), `kiro-cli mcp add --scope global --name backlog --command backlog --args mcp,start` (Kiro). El servidor **resuelve el proyecto activo a partir de las *roots* del cliente MCP** y se re-resuelve al cambiar de *workspace*/`worktree`, o se fija con la variable de entorno `BACKLOG_CWD`. Recursos MCP expuestos con nombre: `backlog://workflow/overview`, `backlog://workflow/task-creation`, `backlog://workflow/task-execution`, `backlog://workflow/task-finalization`.
- **Git**: ficheros Markdown versionados directamente en el repo (`backlog/`, `.backlog/`, o ruta configurable); opcional sin git (`backlog init --no-git`).
- **Vínculo a rama/PR/commit**: no hay comando nativo de vínculo; el patrón documentado es "una tarea = una sesión = un PR" por convención de flujo de trabajo, no aplicado automáticamente por la herramienta.

### GitHub Issues + sub-issues + Projects v2

- **Jerarquía**: hasta **100 sub-issues por padre y 8 niveles de anidamiento** — cita literal: *«You can add up to 100 sub-issues per parent issue and create up to eight levels of nested sub-issues»* ([docs.github.com](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)). CLI: `gh issue create --title "T" --body "B" --parent <N>`, `gh issue edit <PADRE> --add-sub-issue <HIJO>`, `gh issue edit <PADRE> --remove-sub-issue <HIJO>`.
- **Dependencias bloqueantes** (distinto de jerarquía): `gh issue create --blocked-by <N> --blocking <M>`, `gh issue edit <N> --add-blocked-by <M>`, salida consultable con `gh issue view <N> --json blockedBy,blocking` — cita literal confirmada: *«Issue dependencies let you define issues that are blocked by, or blocking, other work»* ([docs.github.com](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-issue-dependencies)).
- **Asignación como (pseudo-)claim**: `gh issue edit <N> --add-assignee <user>` — no exclusivo (§3.1).
- **Vínculo a rama/PR/commit, nativo**: crear rama directamente desde la página del issue ("Create a branch" en la sección "Development" del sidebar), la PR que sale de esa rama se enlaza automáticamente al issue — cita literal: *«When you create a pull request for one of these branches, it is automatically linked to the issue»* ([docs.github.com](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-a-branch-for-an-issue)); función marcada explícitamente como **preview pública, sujeta a cambios**.
- **Projects v2**: automatizaciones nativas y vía API/Actions (visto en el índice de la doc, no explorado campo a campo en esta sesión — **sin verificar en profundidad** el esquema GraphQL completo de `ProjectV2Item`).

### Claude Code agent teams

- **No hay CLI ni JSON pensado para scripts externos** — es un mecanismo interno de la sesión interactiva de Claude Code, no una API pública. El estado vive en ficheros locales (`~/.claude/tasks/{team-name}/`, `~/.claude/teams/{team-name}/config.json`, buzones `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`), pero la documentación advierte explícitamente contra tocarlos a mano: *«The team config holds runtime state such as session IDs and tmux pane IDs, so don't edit it by hand or pre-author it: your changes are overwritten on the next state update»* ([agent-teams.md](https://code.claude.com/docs/en/agent-teams)). **Esto excluye a agent teams de R7 (interfaz independiente de modelo) por diseño**: solo Claude puede participar como *teammate* (selección de modelo limitada a la familia Claude — alias `opus`/`sonnet` — o al modelo del líder; no hay mención de DeepSeek, GPT ni ningún proveedor de terceros como *teammate*).
- **Hooks** como único punto de extensión scriptable: `TeammateIdle`, `TaskCreated`, `TaskCompleted` — permiten inyectar lógica externa (ej. un script que verifique algo y bloquee con código de salida 2), pero no exponen ni consumen el estado del trabajo desde fuera de la sesión.
- **Git**: sin vínculo nativo a rama/PR/commit — es responsabilidad del *teammate* mismo hacer esas operaciones con las herramientas de git de las que dispone.

## 6. Ranking y combinación recomendada

**Confianza global de esta sección: media.** Se basa en lectura directa de documentación y código (alta confianza por candidato individual), pero la comparación entre familias de herramientas tan distintas (spec frameworks vs. work-state vs. función nativa de un arnés) es, en parte, síntesis propia — **se etiqueta explícitamente como inferencia dónde corresponde**.

### 6.1 Spec/descomposición

1. **spec-kit** — más adoptado, mejor documentado, multi-arnés real. Recomendado como generador de la especificación y el `tasks.md` inicial. Riesgo: la propia crítica externa (Böckeler) sugiere que el spec puede no sobrevivir más allá de la vida de la rama — para un flujo que necesita trazabilidad post-implementación (C7), esto exige combinarlo con un sistema de estado del trabajo que sí persista (ver 6.3).
2. **OpenSpec** — alternativa con mejor soporte declarado de multi-arnés (30+ herramientas nombradas explícitamente, sintaxis de invocación por herramienta documentada) y la función `Stores` para specs cross-repo, que resuelve un hueco que A2 dejó abierto. Recomendado si el proyecto cruza varios repos o si se valora la ligereza sobre la rigidez de fases.
3. **Kiro** — único con paralelismo automático por dependencias (waves) como función de producto, no como patrón que haya que montar aparte. Recomendado **como referencia de diseño** (cómo debería verse la ejecución paralela de un `tasks.md`), no como herramienta a adoptar directamente porque es un producto cerrado de AWS con el agnosticismo de modelo sin confirmar en fuente primaria.
4. **BMAD-METHOD** — el más alineado con el patrón "diseño por roles humanos-como-agentes" que menciona la idea de partida del usuario (Opus diseña, ejecutores implementan), pero con menos detalle de artefacto verificado en esta sesión. Candidato a profundizar si D lo requiere.

### 6.2 Estado del trabajo

1. **GitHub Issues + sub-issues + Projects v2** — el único que cumple R6 (sync), R9 (auditoría), R12 (visibilidad/GitHub) y R13 (coste operativo) sin matices ni infraestructura propia, y con R8 sólido (100 sub-issues, 8 niveles). Su fallo real y confirmado es R3/R4 (sin claim atómico ni lease nativos) — **inferencia propia**: esto es solucionable con una capa fina (un label `claimed-by:<agente>` añadido con un script que primero comprueba que no exista, usando la propia API REST con `If-Match`/ETags para CAS — no confirmado que GitHub soporte esto en issues, **sin verificar**), no con una herramienta nueva.
2. **`beads`** — el más completo sobre el papel (único con R10/R11 confirmados de forma nativa: compactación de contexto y memoria de proyecto persistente vía `bd remember`/`bd prime`), pero con la peor evidencia en contra de toda la matriz en R13, con issues abiertas y no negadas por corrupción, demonios huérfanos y datos obsoletos servidos entre sesiones. **No recomendado como pieza única** para una VM de 4 núcleos/7GB sin vigilancia activa del proceso `dolt sql-server`; posible candidato en modo *embedded* (single-writer) si el flujo real es "un agente a la vez coge trabajo", no concurrencia real.
3. **`Backlog.md`** — el mejor equilibrio simplicidad/funcionalidad para R1/R2/R6/R7/R13, con R2 (detección de "listo") especialmente bien resuelto (`isReady` derivado en cada lectura, con `blockingDependencies`/`missingDependencies` explícitos en el JSON). Carece por completo de R3/R4 (igual que Issues) — mismo remedio propuesto: capa fina de claim añadida encima.
4. **Claude Code agent teams** — útil solo dentro de una sesión interactiva única, en una sola máquina, sin persistencia entre reinicios de sesión completos (los *teammates* no vuelven tras `/resume`) y sin agnosticismo de modelo. **No cumple el requisito de "ejecutor intercambiable" del usuario** por diseño: es Claude-only. Recomendado únicamente como mecanismo de paralelismo dentro de una única sesión de diseño/revisión (C5), no como el sistema de estado del trabajo del circuito completo.
5. **`wedow/ticket`** — el más ligero de todos, coherente con R13, pero sin ningún mecanismo de concurrencia (R3/R4 ausentes por diseño, no por bug). Recomendado solo para uso de un agente a la vez, o como inspiración de formato (fichero Markdown con YAML frontmatter, ID como nombre de fichero navegable desde el editor) más que como pieza de coordinación multiagente.
6. **`claude-task-master`**: señal de posible abandono (§4) — no recomendado como pieza central hasta aclarar el estado del proyecto; útil como referencia de "tags/workstreams" para trabajo con múltiples líneas paralelas, mencionado en su documentación pero no verificado en profundidad aquí.
7. **`tasks.md` de los frameworks de spec, solo**: no cumple R3/R4/R8/R10/R11 — es un entregable de la fase de especificación, no un sistema de estado. **No es un candidato independiente**, es la entrada del combinado.

### 6.3 Combinación que mejor cubre el componente (inferencia propia, no una única fuente lo describe así)

Ninguna herramienta cubre R1–R13 completos. La combinación con mejor cobertura agregada, a partir de la evidencia de esta sesión:

**spec-kit u OpenSpec (genera `spec.md`/`plan.md`/`tasks.md`) → GitHub Issues con sub-issues (una por tarea del `tasks.md`, jerarquía épica=spec/tarea=sub-issue) + dependencias `blocked-by` nativas → una capa de claim añadida (script fino, label o campo de Projects v2 con comprobación-antes-de-escribir) para resolver R3/R4, que es exactamente el hueco que Issues no cubre nativamente.**

Justificación por requisito: R1/R6/R9/R12/R13 los cubre GitHub nativamente y sin coste de infraestructura adicional (verificado); R2/R8 los cubren sub-issues + dependencias nativas (verificado); R5 lo cubre el propio identificador de issue de GitHub, sin colisión por diseño (inferencia, no se ha buscado un caso de colisión documentado); R7 lo cubre `gh` CLI con `--json` en cada subcomando (verificado, patrón usado en toda esta investigación); R3/R4 son el hueco real, que ninguno de los candidatos de esta lista resuelve de forma nativa y contrastada — se etiqueta como **el problema abierto más importante que deja esta fase C1 para D**, no resuelto por ningún candidato evaluado con evidencia primaria sólida salvo `beads` (con el coste de R13 en contra) y Claude Code agent teams (con el coste de no ser multi-modelo y no sincronizar entre máquinas).

Alternativa más simple, menor coste de integración pero peor en R9/R12: **spec-kit/OpenSpec → `Backlog.md`** (ficheros Markdown con `isReady` ya resuelto, MCP nativo multi-arnés), con la misma capa de claim añadida encima para R3/R4.
