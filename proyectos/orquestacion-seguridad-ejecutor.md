Aislamiento, catálogo de riesgos y controles por capa para un agente ejecutor que edita código, ejecuta tests y abre PRs.

Informe de un frente de la investigación. Síntesis y decisiones en [[orquestacion-opus-deepseek-informe]].

Fecha de la investigación: 2026-09-24.

Contexto: Claude Code (Opus) orquesta; un modelo DeepSeek vía API oficial actúa como asistente de codificación autónomo que edita ficheros, ejecuta builds/tests en ramas git y abre PRs revisadas por CI. Objetivo: arquitectura defensiva, mínimo privilegio, en una sola VM Linux sin GPU y sin contraseña de root. Criterio: soluciones probadas y mantenidas, no hype.

## 1. Tabla comparativa de opciones de aislamiento

| Opción | Mecanismo de aislamiento | Fuerza de aislamiento | Allowlist de red saliente | Practicidad en 1 VM Linux, sin GPU, sin root password | Estado de mantenimiento (gh api, 2026-09-24) |
|---|---|---|---|---|---|
| **Claude Code sandbox nativo** (Bash sandboxeado) | En Linux: bubblewrap (namespaces) + proxy local (socat) para red; seccomp opcional para bloquear sockets Unix. No es un runtime de contenedores separado, protege solo el propio proceso agente. | Media. Documentado como "filesystem writes kernel-blocked" y proxy de red con allowlist por dominio ([docs oficiales](https://code.claude.com/docs/en/sandboxing)). **Pero**: se han encontrado y explotado 2 bypasses reales — inyección de null-byte en hostname SOCKS5 que burlaba el allowlist de dominios comodín (CVE-2025-66479 en la librería subyacente, sin CVE propio de Claude Code, parcheado en v2.1.90 tras 5.5 meses expuesto) ([oddguan.com](https://oddguan.com/blog/second-time-same-sandbox-anthropic-claude-code-network-allowlist-bypass-data-exfiltration/)); y `sandbox.denyRead` no bloquea la herramienta `Read` de Claude (solo bloquea Bash), permitiendo leer ficheros "denegados" igualmente — hace falta además `permissions.deny Read(...)` como capa independiente ([claudecodecamp.com](https://www.claudecodecamp.com/p/claude-code-sandboxing-how-sandbox-works-and-what-it-doesn-t-protect)). Conclusión: aislamiento a nivel de proceso/usuario, no de kernel; no apto como única barrera para un asistente no confiable con acceso a credenciales. | Alta — no requiere root, se instala con `bubblewrap` + `socat` vía paquetes de usuario ([docs](https://code.claude.com/docs/en/sandboxing)). | anthropics/claude-code: 147.951★, push 2026-09-24, no archivado. |
| **Devcontainers** (spec + CLI) | Contenedor Docker/Podman definido por `devcontainer.json`. Aislamiento = el del runtime subyacente (namespaces de Docker estándar). | Baja-media si se usa tal cual: en VS Code sobre Docker Desktop suele correr con socket Docker expuesto, rutas de host montadas y `sudo` sin contraseña en imágenes oficiales — fuga de aislamiento fácil ([opencomputer.dev / hallazgo replicado en búsqueda](https://opencomputer.dev/guides/podman-vs-docker-untrusted-code/)). Requiere hardening manual (sin socket montado, sin sudo, rootless). | No nativo; hay que montar un proxy (p.ej. Privoxy/mitmproxy) o reglas de red del propio motor de contenedores. | Alta — es el patrón más estándar y documentado, un único binario (`devcontainer` CLI) sobre Docker/Podman rootless. | devcontainers/cli: 2.967★, push 2026-09-17, no archivado. |
| **Rootless Docker / Podman** | Namespaces de usuario; el daemon (o Podman sin daemon) corre como usuario no privilegiado, sin socket root. | Media. Adecuado para código "semi-confiable" con seccomp + AppArmor; **no** es aislamiento de kernel — un escape de namespace compromete el host. Podman es rootless-first y daemonless por diseño, más limpio que Docker para este caso ([búsqueda comparativa](https://opencomputer.dev/guides/podman-vs-docker-untrusted-code/); proyectos dedicados: [agentsbox](https://github.com/mrdaak/agentsbox), [opencode-pod](https://github.com/ThomasBPG/opencode-pod)). | Nativa por rootless: cada red de contenedor puede tener reglas iptables/nftables de salida, o un proxy inyectado como único gateway. | Alta — exactamente el caso de "1 VM sin root password": Podman rootless es first-class citizen. | containers/podman: 32.924★, push 2026-09-24, no archivado. |
| **gVisor (runsc)** | Kernel de aplicación en user-space (Sentry) que intercepta syscalls antes de llegar al kernel del host; Gofer media el acceso a ficheros ([gvisor.dev](https://gvisor.dev/docs/)). | Alta. Es lo que usa Google en producción (GKE Sandbox, Cloud Run) para cargas no confiables. Reduce superficie de ataque del kernel real. Overhead notable en cargas syscall-intensivas (2-3x menos que ptrace con el backend Systrap) ([opensource.googleblog.com](https://opensource.googleblog.com/2023/04/gvisor-improves-performance-with-root-filesystem-overlay.html)). | Se integra como runtime OCI bajo Docker/Podman; el allowlist de red se hace igual que con cualquier contenedor (iptables/proxy), gVisor no añade filtrado de dominios por sí mismo. | Media-alta — existe modo rootless documentado (`dockerd-rootless-setuptool.sh` + `runsc`), pero hay issues abiertos de compatibilidad rootless+GPU y algunos flags experimentales necesarios (`--TESTONLY-unsafe-nonroot`) ([gvisor.dev/rootless](https://gvisor.dev/docs/user_guide/rootless/); [issue #12575](https://github.com/google/gvisor/issues/12575)). Sin GPU no aplica esa limitación. | google/gvisor: 19.415★, push 2026-09-24, no archivado. |
| **Kata Containers** | VM ligera por contenedor (QEMU/Cloud Hypervisor + kernel propio) detrás de una API compatible con OCI/containerd. Aislamiento de hardware real (KVM), no solo namespaces. | Muy alta — cada contenedor tiene su propio kernel; un escape de contenedor no compromete el host directamente. | Igual que cualquier VM: reglas de firewall/proxy en el host o dentro de la microVM. | Baja en el escenario dado: requiere KVM anidado y `/dev/kvm` accesible; el modo rootless existe pero está documentado como limitado y con fallos reportados por usuarios ("Kata claims to support rootless, but I fail to achieve that in many machines", [issue #9591](https://github.com/kata-containers/kata-containers/issues/9591); guía rootless oficial: [how-to-run-rootless-vmm.md](https://github.com/kata-containers/kata-containers/blob/main/docs/how-to/how-to-run-rootless-vmm.md)). En una VM cloud típica sin virtualización anidada habilitada, inviable. | kata-containers/kata-containers: 8.787★, push 2026-09-24, no archivado (proyecto CNCF). |
| **Firecracker microVMs (self-hosted) / E2B** | MicroVM basada en KVM, arranque en ~125ms, aislamiento de hardware por VM ([spheron.network](https://www.spheron.network/blog/ai-agent-code-execution-sandbox-e2b-daytona-firecracker/)). E2B es la capa de orquestación (Nomad+Consul+Firecracker) sobre Firecracker, pensada específicamente para ejecutar código de agentes de IA. | Muy alta — mismo nivel que Kata, aislamiento de hardware por microVM, cada sandbox con su propio kernel. | El propio E2B/infra permite reglas de red por sandbox; auto-gestionado hay que construirlo (iptables/eBPF) igual que con cualquier VM. | Baja para "1 VM sin GPU sin root": Firecracker exige KVM (`/dev/kvm`, típicamente root o grupo `kvm`) y el self-host de E2B es "un proyecto de infraestructura real, no un `helm install`" (Terraform + Nomad + Consul) ([beam.cloud](https://www.beam.cloud/blog/how-to-self-host-code-sandbox); repo [e2b-dev/infra](https://github.com/e2b-dev/infra)). Sobredimensionado para un solo ejecutor. | e2b-dev/E2B: 13.951★, push 2026-09-22, no archivado. e2b-dev/infra: 1.614★, push 2026-09-24, no archivado. |
| **bubblewrap + Landlock** | bubblewrap: namespaces sin privilegios (usado por Flatpak) ([github.com/containers/bubblewrap](https://github.com/containers/bubblewrap)). Landlock: LSM del kernel (desde 5.13, ~2021) que permite a un proceso no privilegiado autorrestringir su propio acceso a ficheros/red ([kernel docs](https://docs.kernel.org/security/landlock.html), [landlock.io](https://landlock.io/)). Se complementan con seccomp-bpf para filtrar syscalls. Es literalmente lo que usa el sandbox nativo de Claude Code en Linux. | Media-alta si se combinan los tres (bwrap + seccomp + Landlock); Landlock reduce la dependencia de namespaces sin privilegios. Sigue siendo aislamiento de proceso, no de kernel completo. | No nativo — hay que enrutar la red a través de un proxy que aplique el allowlist (igual patrón que el proxy local de Claude Code). | Alta — es exactamente el mecanismo ya usado por el sandbox de Claude Code y por herramientas hermanas (Codex CLI usa Landlock en Linux, [codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/08/codex-sandbox-platform-implementation/)). No requiere root. | containers/bubblewrap: 8.823★, push 2026-09-22, no archivado. Landlock es parte del kernel Linux (no aplica gh api). |
| **OpenHands runtime** | Contenedor Docker donde corren las acciones del agente (ediciones, shell, tests). Runtime "remoto" gestionado (`runtime.all-hands.dev`) también disponible como servicio SaaS. | Media — depende del hardening del contenedor Docker subyacente; no añade aislamiento de kernel por sí mismo. Hay una feature request abierta para backend microVM (QEMU) como alternativa a Docker, aún no disponible ([issue #13203](https://github.com/OpenHands/OpenHands/issues/13203)). | Sí, de forma explícita: `SANDBOX_NETWORK_DISABLED=true` corta toda salida; o `SANDBOX_ADDITIONAL_NETWORKS` para redes controladas; recomendación documentada de default-deny a rangos privados y endpoint de metadatos con allowlist de registries ([docs.openhands.dev](https://docs.openhands.dev/openhands/usage/v0/runtimes/V0_docker)). | Alta — es un contenedor Docker estándar, funciona en cualquier VM con Docker Engine (rootless posible). | All-Hands-AI/OpenHands: 89.089★, push 2026-09-24, no archivado (el más activo de la lista con diferencia). |

**Recomendación de arquitectura para el escenario (1 VM Linux, sin GPU, sin root password):** rootless Podman como base + gVisor (`runsc`) como runtime OCI para la ejecución del código de DeepSeek, con un proxy de salida (allowlist explícito de dominios: registry npm/pip, GitHub API, api.deepseek.com) como único camino de red — el mismo patrón de "dos capas de contención" que describe la comunidad para rootless Docker+gVisor. Kata/Firecracker quedan descartados por requerir KVM y privilegios de los que la VM objetivo carece; el sandbox nativo de Claude Code es un complemento razonable para el propio orquestador pero no debe ser la única barrera dado su historial reciente de bypasses de red.

## 3. Controles recomendados por capa

### Credenciales
- Preferir **GitHub Apps** con tokens de instalación de corta vida sobre PATs clásicos o de larga duración; el `GITHUB_TOKEN` nativo de Actions ya es de corta vida, ámbito acotado al repo/workflow y se revoca al terminar el job. [github.blog — fine-grained PATs](https://github.blog/security/application-security/introducing-fine-grained-personal-access-tokens-for-github/), [moderngitacademy.com](https://moderngitacademy.com/security/repository/fine-grained-tokens/)
- Si se usa PAT, que sea **fine-grained**, con expiración obligatoria y alcance mínimo (repos concretos, permisos concretos): "un token con 90 días restantes es peligroso como máximo 90 días". [visma-prodsec/github-token-guide](https://github.com/visma-prodsec/github-token-guide)
- Nunca credenciales de larga vida dentro del entorno del agente. El propio sandbox de Claude Code ofrece un mecanismo de "masking" (sustituye el secreto por un centinela y solo el proxy de salida lo reinyecta hacia hosts explícitamente permitidos) — patrón útil a replicar aunque no se use ese sandbox como aislamiento principal. [docs oficiales](https://code.claude.com/docs/en/sandboxing)
- Clave DeepSeek API: tratarla igual que cualquier secreto de proveedor externo — nunca en el entorno del ejecutor si se puede enmascarar/inyectar solo en el proxy de salida hacia `api.deepseek.com`.

### Red / egress
- Allowlist explícito de dominios de salida (registry de paquetes, GitHub API, `api.deepseek.com`) aplicado en un proxy o en el runtime del contenedor — no confiar únicamente en el allowlist del propio orquestador (ver bypass documentado arriba).
- Default-deny a rangos privados y al endpoint de metadatos de la nube, patrón recomendado explícitamente para runtimes de agentes. [docs.openhands.dev](https://docs.openhands.dev/openhands/usage/v0/runtimes/V0_docker)
- `SANDBOX_NETWORK_DISABLED=true` (o equivalente) cuando una tarea no necesita red en absoluto.

### Branch protection / revisión
- **Rulesets** de GitHub (o branch protection rules) con número mínimo de aprobaciones, descarte automático de aprobaciones al llegar nuevos commits ("dismiss stale reviews"), y **firma de commits obligatoria** — las rulesets verifican todos los commits nuevos que no sean alcanzables desde otra rama, a diferencia de las branch protection rules clásicas. [GitHub Docs — About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [GitHub Docs — Managing a branch protection rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/managing-a-branch-protection-rule)
- El PR de un agente nunca debería poder auto-mergearse; requerir revisor humano explícito, no otro agente.

### CI gates para código escrito por IA
- SAST + SCA + secret scanning + escaneo de imagen en cada PR, con bloqueo automático en hallazgos críticos; cerca de la mitad del código generado por IA lleva algún fallo de seguridad, y el desarrollo asistido por IA aumenta el ritmo de commits 3-4x, por lo que el pipeline de gates es la contención real. [decryptiondigest.com — DevSecOps Implementation Guide](https://www.decryptiondigest.com/blog/devsecops-implementation-guide)
- Generar **SBOM** en el build para inventario/triage; distinguir dependencias directas vs. transitivas y runtime vs. test. [Security Boulevard — SAST/DAST/SCA en CI](https://securityboulevard.com/2026/09/integrating-sast-dast-and-sca-tools-into-ci-pipelines/)
- Lockfiles / allowlist de dependencias con mecanismo de baseline (fichero versionado de hallazgos aceptados, con motivo y caducidad) para poder activar el gate en bloqueo sin bloquear todo el histórico de golpe. [misma fuente]

### Calidad real de los tests (evitar que el agente "apruebe trampeando")
- Regla explícita: el agente no puede borrar ni debilitar un test existente; si toca un test, ese cambio es el objeto principal de revisión, no un detalle. [dev.to — Your agent went green by weakening the tests](https://dev.to/brasthapp/your-agent-went-green-by-weakening-the-tests-1iha)
- **Mutation testing** como gate en CI limitado a los ficheros tocados por el PR (no toda la base de código, para que sea viable en tiempo): PIT (Maven) y Stryker soportan umbrales de "mutation score" configurables como quality gate. [awesome-testing.com](https://www.awesome-testing.com/2026/08/mutation-testing-for-agent-written-code), [augmentcode.com](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)
- Cobertura como señal necesaria pero no suficiente — combinar siempre con mutation score, nunca cobertura sola como gate único.

## 5. Dudas abiertas

1. **No se verificó** si DeepSeek ofrece algún compromiso contractual de zero-data-retention o residencia fuera de China para clientes empresariales de la API — la documentación pública no lo confirma de forma universal; si existe un acuerdo empresarial distinto, habría que pedirlo directamente al proveedor.
2. **No se verificó** el estado exacto de la vulnerabilidad SOCKS5 null-byte en la versión de Claude Code que se vaya a desplegar en producción — solo se confirma el rango de versiones afectadas (2.0.24–2.1.89) y el parche en 2.1.90; conviene comprobar la versión instalada.
3. No se encontró benchmark cuantitativo reciente y comparable de overhead (gVisor vs. Kata vs. Firecracker vs. bwrap+Landlock) en syscalls típicos de un build/test de un proyecto de software real (compilación, tests, npm/pip install) — los datos de overhead encontrados son genéricos o de otros escenarios (Sentry/Systrap).
4. La tabla de OWASP Top 10 Agentic Applications 2026 lista solo 4 categorías con detalle (ASI01, 03, 09, 10) en las fuentes secundarias consultadas; no se obtuvo la lista completa de las 10 desde una fuente primaria única — recomendable leer el PDF/recurso original en `genai.owasp.org` para la lista completa de ASI01–ASI10 antes de diseñar controles contra cada una.
5. No se investigó en detalle el runtime de OpenHands en modo "remote" gestionado por All-Hands-AI (`runtime.all-hands.dev`) como alternativa SaaS a levantar la infraestructura propia — quedó fuera de alcance por ser el escenario "self-hosted en 1 VM".
